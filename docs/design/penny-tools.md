### Penny Tools (`src/lib/penny/tools/`)

addStop, updateStop, deleteStop, addLeg, updateLeg, deleteLeg, addRoute, updateRoute, deleteRoute, getRoute, resolvePlace, addTask, updateTask, updateVehicle, renameTrip, reportPosition, submitIdea, checkTripFeasibility, planFuelStops, declareFuelState, extractTripIntent — registered in `index.ts`, shared helpers in `shared.ts`

**Penny does not author derived fields (2026-09-09).** Three facts she used to invent are now computed server-side, because a fact the database already knows is not the model's to write:
  - **Split-point names.** `get_route`'s `suggested_split` was bare lat/lng, so she named the days herself — "Texas Panhandle", "Albuquerque area" (trip `ab824cde`), neither navigable. Each split now carries `end_name`, reverse-geocoded server-side. **Not Google:** the one key does NOT have the Geocoding API enabled (probed 2026-09-09 — `REQUEST_DENIED`, "not authorized to use this service", the same shape as the legacy-Places-SKU outage), so it is **Nominatim** (`lib/osm/nominatim.ts`), whose terms are the design: a real identifying `User-Agent` is mandatory (`NOMINATIM_USER_AGENT`), 1 req/s so the module serialises, and every failure returns null rather than throwing —  a missing name must never fail a plan.

    **The label, and the point it labels, were both wrong (2026-09-21).** Two-day Girona → Annecy at a 4 h cap came back as `Girona → Tavel, Occitania` / `Tavel, Occitania → Annecy, Auvergne-Rhône-Alpes`. Three separate defects, and none of them the model — the swap to Haiku (`18afc662`) and the server-side naming (`a4edc0ae`) landed on the same day, so the change got blamed on the model; reverting to Sonnet would have changed nothing, because by then Penny was using `end_name` verbatim exactly as instructed.

      1. **`address.state` is not a qualifier outside a handful of federal countries.** `formatPlaceLabel` did `state ?? country`, written and tested entirely against US payloads, and `state` in France is the *région*. It is now an allowlist of country codes where the sub-national unit is what people actually say (`us ca au br mx in`); everywhere else the country qualifies, so it reads "Tavel, France". Every test payload is now CAPTURED from live Nominatim (`src/lib/osm/__fixtures__/`, regenerate with `scripts/capture-nominatim-fixtures.mjs`) — the test meant to prove the non-US path asserted against `{ city: 'Girona', country: 'Spain' }`, a shape Nominatim has never returned (it returns `Catalunya` / `España`), so it passed while the path was broken.
      2. **Nominatim answers in the local language unless asked not to**, so a Spanish split point read "Girona, Catalunya" and an Italian one "Modena, Italia". The request now carries `accept-language=en`; `reverseUrl` is exported purely so a test can assert it is still there, because its absence is invisible in the response.
      3. **The split point itself was a village.** `split-route.ts` splits at exactly 50% of drive time and the naming step labels whatever is nearest; the 50% mark fell outside Tavel, population ~1,800. The split point is not a fact — the daily CAP is the fact, and the point is a choice inside a tolerance. `lib/penny/splitPointNames.ts` now walks the polyline outward from the planned split and takes the first `city` or `town`, subject to neither neighbouring day exceeding the cap and the move staying inside `tolerance_minutes` (default 25, probed in 12-minute steps, at most 5 Nominatim calls per split). On the reported trip that is +11 minutes to Orange, a town on the A7 and the junction a driver would pick anyway. It costs ONE call when the planned split already lands somewhere real — the planned point is always probed first — and it degrades to the planned split and its own label whenever nothing qualifies. `splitPointNames.test.ts` runs the real algorithm over that trip's real geometry and real captured Nominatim answers; `split-route.ts` is decomposed into `planSplitIndices` + `legsFromSplitIndices` so the legs are rebuilt from the moved indices rather than from a second copy of the uniform-speed maths.
  - **Drive-leg titles** are `start → end`, derived in `addLeg` and in the `update_leg` dispatcher from the endpoints the write leaves behind (`lib/legTitle.ts`). Haiku titled a leg ending in Marfa "Austin → Big Bend (Day 1)" (trip `1b1cc80b`); the row already carries both endpoints, so a supplied title is a second copy free to disagree. Rest legs keep their own title — a base day is not a journey. Four wrong titles on `1b1cc80b` were backfilled.
  - **`trips.end_date`** is the last leg's date, re-derived after every apply by `syncTripEndDateFromLegs` (`repos/trips.ts`), and **`rename_trip` no longer has an `end_date` field** — she had to remember to send it and Haiku did not (`ab824cde`: 13 legs, `end_date` NULL; backfilled to 2026-10-20). It reads `lastDayFromSchedule`, NOT `legs.dates`: that column is null on essentially every row because leg dates are computed at read time by `getTripFull`, so deriving from it would have silently written nothing forever. `renameTrip.test.ts` fails if the field returns.
  - `resolve_place` additionally returns **`name_for_leg`** — the place qualified by state or country ("Monument Valley, UT"), derived by `lib/placeName.ts` from the `displayName` and `formattedAddress` Google already sends. No field-mask change, so no SKU change. Conservative by design: it qualifies only when confident and otherwise returns the label untouched.

- **`place_id` is the routable identity, and it is opaque (2026-09-11).** `resolve_place` returns it on the resolved match AND on every candidate; `get_route` takes `origin_place_id` / `destination_place_id` and a `place_id` per waypoint, and returns `routable_start` / `routable_end` — the points Directions actually snapped to — which Penny writes onto the leg *in preference to the coordinates she passed in*. She forwards the id untouched and never authors, edits or invents one, the same rule she already follows for coordinates. The prompt states the whole flow in `<place_resolution>`; `routablePlacesGuard.test.ts` fails if any hop drops it again, which this seam has now silently done once.
- **resolvePlace** is the deterministic name→coordinates lookup (`src/lib/google/geocode.ts`, Google Places Text Search → Geocoding fallback). It is the ONLY sanctioned source of lat/lng for a named location — the Penny prompt forbids her from authoring coordinates from her own knowledge (the "dropped me near the right city, wrong spot" bug). Returns a tri-state with granularity (precise/locality/area/country); a coarse centroid for a query that named a specific place is treated as too-vague and Penny clarifies instead of pinning. A LOOKUP tool (runs inline, doesn't write to the DB).
  - **A pasted Maps link that did not resolve can still carry a `name_hint` (2026-09-26).** The server resolves every Maps link before Penny sees the turn (`resolveMapsLinksInMessage`, `<resolved_maps_links>`). When it recovers a name or address from the link (og:title, the redirect's `q=`, or the page's embedded link) but no coordinates, the unresolved entry carries `name_hint`, and `<maps_link_handling>` tells Penny to say what the link points to and call `resolve_place` ONCE with that hint, acting on its status as usual. Without a hint she asks for the place name or raw lat/lng. The coordinates still come only from the server or `resolve_place` — the hint is a query, never a location. Every miss (and every paid-geocode rescue) writes a `penny:maps-link` usage row carrying the resolver's `stage`, so it shows in `/admin/errors`.

- **reportPosition** records the driver's real-world progress: sets the trip's `current_leg_id` + position anchor, re-points the upcoming leg to start where they are, and re-anchors the calendar from now. This is the lever behind "I'm in X, didn't reach Y".
- **submitIdea** logs an unsupported-but-reasonable feature request to `usage_events` (provider `penny:user-idea`) so the team can read it — keeps Penny from faking capabilities the app lacks (e.g. fuel prices).
- **declareFuelState** (2026-07-12) records the driver's stated CURRENT tank ("I only have 150 km in the tank") — the third fuel category alongside range preferences (Settings-only) and fuel requests (Finn). Writes `trips.declared_range_km/_leg_id/_at` (migration 0021); Finn's tank walk treats it as the remaining-range baseline at the anchor leg's start (`resolveDeclaredTankAnchor` in `server/fuel.ts` + `declaredBurnedKmAtStart` in `fuelTankState.ts`), superseded automatically by any real fuel stop after the anchor. Runs INLINE (a lookup with a DB write, like plan_fuel_stops) so a same-turn plan_fuel_stops re-run sees it; it also invalidates the fuel cache for the anchor leg onward. Prompt: `<vehicle_preference_updates>` teaches the three-way distinction + "ask one clarifying question instead of pushing back" when a number is ambiguous. Origin: trip d0b5741b — driver said he'd run dry at 150 km, Finn's stop sat at 181 km off the saved 500 km range, and Penny could only argue or point at Settings. Known gap: declarations don't expire on report_position — a stale one biases Finn conservative (extra dismissable stop) until a fuel stop passes or a new declaration lands.
