## Working with this codebase

- **Schema changes:** Edit `schema.ts` → `npm run db:generate` → `npm run db:migrate`
- **`timestamp` without time zone + drizzle = a wrong answer on any non-UTC database.** Postgres stores a `timestamp` (no tz) as the server's local wall clock; drizzle reads it back as UTC. They agree only when the database runs in UTC, which Neon does — so production and CI are fine and this is invisible there. Anywhere else the arithmetic is silently off by the offset. **Confirmed defect (2026-09-01):** `email_otp_codes.created_at` is such a column, so `getExistingOtpAgeMs` returns a NEGATIVE age on a non-UTC database, the 60-second OTP resend cooldown never expires, and **every resend is a 429 forever** — a user who never receives their sign-in email can never ask for another. It also made the iOS sign-in flow unable to fail locally while it failed on every CI run, one bug hiding another. `scripts/ios-e2e-local.sh` pins its cluster to UTC so a local run reaches the same branch CI does. **FIXED — migration 0032 (2026-09-04) converts all 43 such columns to `timestamptz`**, so `timestamp` without a zone should no longer appear anywhere in `schema.ts`; keep it that way, and declare any new column `{ withTimezone: true }`. Measured on a UTC-7 session before and after: the same age arithmetic read 25200s (exactly the offset) via `timestamp` and 0s via `timestamptz`. The five NextAuth-shaped `{ mode: 'date' }` columns went with them — `sessions.expires` decides whether you are signed in and `email_otp_codes.expires` whether a code is still valid, which is the same defect with worse consequences. `USING <col> AT TIME ZONE 'UTC'` in that migration is load-bearing: without it Postgres converts using the SESSION's zone, which would reintroduce the ambient-zone dependency at migration time.
- **The migration chain cannot be replayed from an empty database, and `0000 → 0028` has never executed anywhere.** Production was bootstrapped with `drizzle-kit push` (see the header of `scripts/seed-migration-journal.ts`) and every preview branch is a copy-on-write clone of production, so both start from a database that already has the schema and only ever apply the newest file. Two known blockers, found 2026-09-01 by pointing `db:migrate` at a genuinely empty database: `0005_mute_meltdown` and `0006_nightly_replan` both `CREATE TYPE "trip_status"` and both `ADD COLUMN trips.trip_status`, the second unguarded (`42710`); and `0002_magical_joystick` calls `setval(seq, 0)` on an empty `chat_history`, which is out of range for a serial (`22003`). There may be more — nothing has ever got past the second one. **Consequences to keep in mind:** a new contributor cannot create a working database from the migrations, `db:migrate` is only ever exercised as "apply the newest file to an existing schema", and the CI rehearsal against the preview branch proves that and nothing more. A fresh database is bootstrapped with `db:push` + `seed-migration-journal.ts` instead, which is what `scripts/ios-e2e-local.sh` does. Fixing the chain means editing applied migrations, which is safe on the deployed databases (drizzle picks what to run by folder TIMESTAMP, not by file hash) but unverifiable against them — so it is a deliberate piece of work, not a drive-by.
- **New API route:** Create `src/app/api/<resource>/route.ts`, add repo if needed
- **New Penny tool:** Add to `src/lib/penny/tools/`, register in `index.ts`
- **E2E tests:** Playwright starts the app itself (webServer) and seeds fixtures over HTTP via `/api/test/*` in `global-setup.ts` — no manual seed step. In CI they run against an ephemeral Neon branch.
