## Architecture

```
src/
  app/
    api/              # REST endpoints (see API Routes below)
    trips/            # Trip list + [tripId] workspace (TripWorkspace.tsx)
    admin/            # Admin dashboard: users/, vehicles/, chats/, errors/, announcements/, deleted/
    page.tsx          # PUBLIC landing page (2026-09-24): hero video, how it works, example prompts, the dogs, the 32 countries. No auth() — ungated in webAccessCoverage.test.ts. Its pieces (video env vars + 0.6x rate, screenshot list, country list) live in components/landing/; the clip is on Vercel Blob, never in git.
    signin/           # What `/` used to be: requireWebAccess(), then /login or /trips. The PWA manifest's start_url.
    login/            # OTP + Google auth flow (verify/ sub-route)
    error.tsx         # The app's ONLY error boundary. Branches on `error.digest` so an unreachable session store says "you have not been signed out" instead of the generic line; Try again calls reset(). Before it existed every server exception rendered Next's stock "Application error" screen.
    settings/         # User settings page (Vehicle profile + the Danger zone / delete-account section)
    (legal)/          # PUBLIC pages, route group so URLs stay /privacy /terms /support.
                      # No auth() call anywhere in here — Google brand verification and
                      # Apple App Review fetch them anonymously. /support is the Support URL
                      # submitted to App Store Connect; changing the path means editing the listing.
    vehicle-setup/    # Vehicle onboarding
  components/
    ChatPanel.tsx     # Penny chat UI
    PennyPlanningVideo.tsx  # The dog-fetch clip Penny "sends" at the start of the post-onboarding full-trip build (the one turn we can predict will be long). Renders a persistent, looping, iMessage-style video bubble inside a REAL Penny message (ChatPanel inserts a UI-only `planningMedia` message at handoff via `sendChatMessage(..., insertPlanningMedia=true)`), so it stays in the transcript and the user can scroll back to it — it no longer vanishes when her reply streams in. Not persisted to chat history (session-only; gone on reload). Every other turn keeps the bare typing dots. Plays at natural 1x; asset URLs carry `?v=N` (ASSET_VERSION) to bust a cached old stub; degrades to poster (reduced motion) or nothing (asset: public/penny-planning.mp4 + .jpg). NOTE: PennyPlanningLoader.tsx is now a deprecated re-export shim — safe to delete. **RESUMES ON FOREGROUND (2026-09-08)** — this was a real bug and neither platform did it. expo-video pauses every non-`staysActiveInBackground` player when the app backgrounds and its `onAppForegrounded()` is an EMPTY function body (`expo-video@3.0.16/ios/VideoManager.swift`); on the web, `autoPlay` is a load-time attribute that never fires twice. So backgrounding the app once during a planning turn left a frozen frame for the rest of it — and since the clip is the only thing on screen saying Penny is still working, and the turn routinely runs 2-4 minutes, that reads as an app that has died (reported exactly that way). Both components now re-issue `play()` on foreground (`AppState` / `visibilitychange`+`focus`+`pageshow`), with Reduce Motion still winning. Guarded by `src/lib/planningClipResumeGuard.test.ts` (source-text, since `mobile/` has no runner) and jsdom cases in `PennyPlanningLoader.test.tsx`. **Native port (2026-09-04): `mobile/components/chat/PennyPlanningVideo.tsx`** on `expo-video` (muted, looping, `mixWithOthers`, Reduce Motion → poster, player error → nothing), rendered by the native ChatPanel off the same `planningMedia` flag; until then the app sent the caption alone. The assets are COPIES in `mobile/assets/` (Metro cannot reach `public/`; bundled, not fetched, so the clip is there with no network) — replace all four together. Adding `expo-video` is a dependency change, so that merge was a native build, not an OTA.
    TripMap.tsx       # Google Maps view. Renders per-leg route polylines, leg-start + final-destination markers, AND stop markers (fuel = gold square, user-added 'other' = slate square) flattened from `legs[].stops`. Stops are clustered in SCREEN SPACE via `lib/mapClustering` (re-runs on map 'idle'); a count bubble expands (fitBounds) on click. Desktop hover (matchMedia '(hover: hover)') shows a stop tooltip; click a stop OR leg marker fires `onStopSelect`/`onLegSelect` → parent opens it in the list (TripWorkspace `focusInList`). Stops are LAZY (option B): only days already opened in the list have stops in the data, so a never-browsed trip shows a quiet "Open a day to load its fuel stops" hint instead of an empty map. No new npm dep — clustering is the in-repo grid clusterer, deliberately NOT @googlemaps/markerclusterer (avoids mutating macOS node_modules from the Linux build sandbox).
    Itinerary.tsx     # Leg/stop/route display. `focusTarget` ({legId, stopId, nonce}) from a map marker click expands the owning leg (revealing it past the lazy window / "behind you" fold), scrolls the leg ([data-leg-id]) or exact stop ([data-stop-anchor]) into view, and briefly rings the stop (highlightStopId → LegCard → StopsSection).
    TasksSection.tsx  # Trip tasks
    DeviceLocationContext.tsx  # THE client GPS pipeline (2026-07-12): owns the one on-load location prompt, a live watchPosition, and a Permissions-API onchange subscription (grant-after-mount activates consumers live). TripWorkspace's position report + useNextStop (smart nav) consume it; nothing else may call the Geolocation API. Since 2026-09-04 it also owns the ONE reverse geocode per session (`place` / `placeResolved`): the position report, the onboarding origin chip and the composer placeholder all read that one label.
    ViewportHintContext.tsx / ViewportHintFromCookie.tsx  # The viewport hint (item 8, 2026-09-04): `useViewport` takes its INITIAL value from a cookie the root layout's inline script writes, so a phone's reload renders the mobile tree first instead of painting the desktop workspace and swapping. See `lib/viewportHint.ts`.
    LocationSection.tsx  # Settings → Location as a SWITCH (2026-09-04). Off→on calls `request` (the browser dialog). On cannot be switched off by a page, so it sits checked+disabled with a sentence naming the address-bar control; native (`mobile/components/LocationSection.tsx`) is live both ways because iOS has `Linking.openSettings()`.
    stops/            # StopCard, StopsSection (with tests). No paste row since 2026-09-04 — see the item 5 note under Schema.
    AnnouncementModal.tsx  # One-time announcement popup
    EntitlementNotice.tsx  # Web soft block. SERVER component (no fetch, no flash of a "+ New trip" button the account can't use) rendering the per-blockReason copy from `lib/paywallCopy`. The trips page decides separately whether the list below it still renders — `refunded`/`revoked` are the only states that close existing trips.
    PurchaseOptions.tsx  # What the web offers a blocked account: the App Store button, then the promo field. A plain block, not a dialog — `PurchaseSheet` wraps it in a modal for Penny's bubble and the pane scrim, and `EntitlementOverlay` renders it inline, because that overlay is already a dialog and opening a sheet on it was two stacked modals (2026-09-22). One component, so the surfaces cannot drift.
    (+ AppNavbar, BottomNav, MobileFooter, Spinner, StatusBadge, etc.)
  lib/
    api.ts            # Client-side API helper
    paywallPaths.ts   # The two allowlists: `PUBLIC_PATH_PREFIXES` (no session — imported BY middleware.ts, single source of truth) and `PAYWALL_EXEMPT_PREFIXES` (signed in, not entitled: adds /settings, /api/me, support, analytics). /privacy /terms /support are explicit entries in both; `paywallPaths.test.ts` fails if they leave, which is the unit-level half of e2e/legal-pages.spec.ts
    paywallCopy.ts    # The four web block messages, one per BlockReason, sharing no string. Trial/subscription-over are sales moments; usage_cap and revoked point at support and never accuse. `APP_STORE_URL` reads NEXT_PUBLIC_APP_STORE_URL (falls back to an Apple search URL — the numeric id only exists after first submission). `APP_STORE_CTA_LABEL` is the web sheet's one button and says what the tap DOES ("Download the app") — "Continue" reads as "continue in this browser", the one thing the web cannot do with a purchase. **The web `PurchaseSheet` shows NO price rows** (2026-09-10) except on the allowlisted fake-purchase path: off it there is nothing to choose — the plan is picked in the iPhone app — so a "Choose a plan" list was two buttons that did nothing, and the promo field now sits under the primary action. The prices still travel in the `/api/me/entitlement` payload because Penny's bubble quotes them
    internalAccounts.ts # Which `users` rows are OURS, for COUNTING users only (2026-09-10). `INTERNAL_EMAIL_PATTERNS` is one list of regex sources shared by two engines — Postgres `~*` in `getAdminOverview`, `RegExp` in `isInternalAccountEmail` — so keep to the syntax subset both read identically. **The two halves are tight for opposite reasons:** `*.feraltravels.com` is a safe wildcard because signing up needs a one-time code at an address on a domain we own, while `samuelashirley+…@gmail.com` is a PUBLIC namespace anyone can sign up into, so it matches only the dated shape the owner uses (`+26.6.26.1`) — a wildcard there would hide a signup flood, which is the one thing most worth seeing. Too tight shows one of our rows in the count (visible); too loose hides a real person forever (invisible) — when in doubt leave the pattern out. `getAdminOverview` returns `internalUsers` beside `totalUsers` and /admin PRINTS it ("22 ours, not counted") rather than quietly subtracting, because a pattern that starts matching real signups is otherwise undetectable. Only the user-COUNT cards filter: the user list, the top-spender table and every spend figure stay unfiltered — a fixture that spent $7 still spent $7, and the list is where you go to delete these rows. Deliberately NOT `isCompedEmail`/`FIXTURE_EMAIL_PATTERN`/`TEST_PURCHASE_EMAIL_PATTERN`, which are security boundaries and stay narrow; this is a reporting filter and is broader than all three.
    models.ts         # Central registry of hardcoded Anthropic model IDs (PENNY_MODEL, DATE_PARSE_MODEL, RANGE_ESTIMATE_MODEL, ONBOARDING_SCAN_MODEL)
    purchaseMode.ts   # The purchase sheet's mode (test / store / unavailable) as ONE pure decision, mirrored to the app (2026-09-07). `unavailable` carries a REASON — `no_key` (no RevenueCat key in this build), `store_empty` (RevenueCat reached the store and StoreKit resolved no products: the Paid Apps Agreement / product metadata, iap-setup.md §1–§2), `store_error` (the offerings call threw), `no_match` (ids disagree), `no_plans` (the server list did not load) — and since 2026-09-21 the CUSTOMER copy (`unavailableMessage`) never names our paperwork, while the five-way developer reading lives in `purchaseDiagnostics.ts`, reached only as `__DEV__ ? require(...) : null` so a release bundle does not contain it (decision E12, `purchaseCopyGuard.test.ts`, the release-bundle check in CI). The five-way split exists because all five once rendered one line and the line was read as a UI bug when it was Apple's paperwork. NOTE RevenueCat THROWS `CONFIGURATION_ERROR` (23) for "no products fetchable", it does not return an empty offering — `mobile/lib/purchases.ts` maps that one throw to the empty answer. `manageSubscriptionAvailable` wraps `canManageAppleSubscription` (in `types/entitlement.ts`, exhaustive over the twelve states): the "Manage subscription" link is hidden for `trial*`/`comped` (no row has ever existed — Apple's screen is an empty list) and for `promo`/`admin` rows (nothing at Apple), shown for every other state, live or lapsed, and flips on the fresh payload after a purchase.
    planStatusLine.ts # Pure AccountState -> one line for Settings -> Plan ("Free trial — 3 days left", "Subscribed"). Exhaustive switch with a `never` default, so a thirteenth state fails `tsc` rather than rendering a blank line. Mirrored to mobile; `planStatusLine.test.ts` asserts all twelve, that `subscribed_watch` reads exactly like `subscribed` (it is an admin threshold and none of the user's business), and that a lapsed trial is never told WHICH way it lapsed
    coords.ts         # Coordinate parsing/formatting (sync; Google/Apple Maps URLs, lat/lng)
    legTitle.ts       # Pure "a drive leg's title is start → end" (deriveDriveLegTitle/resolveLegTitle) — derived, never authored
    placeName.ts      # Pure "Monument Valley" + "Monument Valley, UT 84536, USA" -> "Monument Valley, UT" (qualifiedPlaceName)
    osm/
      nominatim.ts    # Server-side reverse geocode (coords -> place name) for get_route split points. Google's Geocoding API is NOT enabled on the one key. Mandatory identifying User-Agent, 1 req/s, never throws
    coordsResolve.ts  # Server-side Maps URL resolution (short-link redirects; scans page body for !3d!4d/@lat,lng; extracts the embedded google.com/maps?q=<addr> link and geocodes it; og:title place name as a last resort); used by Penny chat enrichment (`resolveMapsLinksInMessage`) — the ONLY paste path since the day-card row and `api/coords/parse` were removed 2026-09-04. NOTE (2026-07-01): short links MUST be fetched with a CRAWLER User-Agent (`SHORT_LINK_USER_AGENT` = facebookexternalhit) — a browser UA gets maps.app.goo.gl's JS-only interstitial with no coords/name/og-tags (the "links won't resolve" bug); the crawler UA is what makes Google embed the destination `?q=<address>` link that `extractEmbeddedMapsQuery` reads. Do NOT switch to a browser-like UA.
    google/geocode.ts # Deterministic name/address/city → coords (Places Text Search → Geocoding fallback). Tri-state result w/ granularity. Backs the resolve_place Penny tool; the ONLY name→coords path (no LLM coordinate guessing)
    maps.ts           # Google Maps URL builders. `buildGoHereUrl(lat,lng)` (2026-09-04) is THE "take me here" link — `/maps/dir/` with `dir_action=navigate` and NO origin, so Maps routes from the device. Every stop row, the NEXT STOP button and StopCard use it; `goHereLinksGuard.test.ts` fails the suite if a component hand-builds the `/maps/search/?api=1&query=` pin again. `buildMapsSearchUrl` stays for FINDING things near a point (park route links).
    reverseGeocode.ts # Best-effort client coords→place label via the Maps JS Geocoder (importLibrary('geocoding')); forgiving (any failure → null). Feeds the device-location place name posted from TripWorkspace on app open.
    mapClustering.ts  # Pure screen-space grid clusterer (clusterPixels) for TripMap stop markers — dependency-free stand-in for @googlemaps/markerclusterer. Unit-tested.
    directions.ts     # Client directions logic
    gpx.ts            # GPX file parsing
    units.ts          # Unit conversion. `formatKm` / `approxDistance` / `formatKmDual` all render in the USER'S unit — miles and no km for imperial since 2026-09-04 (the "teach metric: km primary, (mi) secondary" decision was reversed). `noHardcodedUnitsGuard.test.ts` fails the suite on any `${n} km` / `'390 km'` literal in `src/components`, `src/app` (not `api/`), `mobile/components`, `mobile/app`; a prose line that needs one carries `// units-literal-ok`.
    viewportHint.ts   # The `tp-viewport` cookie: written before first paint by the root layout's inline script, read by the dynamic pages through ViewportHintFromCookie. See item 8 note under Conventions.
    pennyRunStore.ts  # Which trips have a Penny turn in flight, keyed by tripId — MODULE state, mirrored to mobile. Both halves of "Penny is working" used to be screen `useState` (`thinking` in both TripWorkspaces, `loading` in both ChatPanels), and both start false — so ANY fresh mount of the chat screen rendered READY over a live turn. Measured 2026-09-11: `penny_turns.status` read `running` at 12:51:48 and 12:52:11 while the live iOS view hierarchy at 12:52:10 held a text node `READY` and no `THINKING` node. A SET of turn keys, not a boolean: two mounts can track one turn (the sender, still streaming; and a later mount that hydrated from the server), and a boolean lets whichever finishes first clear the indicator out from under the other. NOT the only source of truth — it is per-process, so both ChatPanels ask `GET /api/trips/[id]/turns` (no key) on mount and believe the server; `isTurnInFlight` counts `queued` as well as `running`.
    lastOpenTrip.ts   # The trip most recently open, session-scoped module state, mirrored to mobile. LIST/MAP/CHAT are tabs OF a trip, but BottomNav is also mounted where no trip is in scope (Settings, the trips list) — there all three used to `router.push('/trips')`, so tapping CHAT mid-answer dropped the driver on a list of trips instead of back in the conversation. `tripTabDestination(tab, tripId)` is the whole decision, and returns a template-literal type rather than `string` so Expo Router's `Href` takes it without a cast (`as '/trips'` is the only cast that compiles, and it is a lie about the value). Nothing remembered still means the index.
    planReady.ts      # The deterministic message when the FIRST full plan lands (2026-09-08), mirrored to mobile/shared. Penny's handoff reply used to be the whole plan recited back — route, trade-offs, tasks, closing question — several hundred words after a 2-4 minute wait, restating what the list already shows. Now a `plan_ready` chat row carries fixed copy ("Trip is planned — head over to the list view" + how to set a day's destination from a Maps link) and each client owns its LAYOUT: a list icon, and "list view" as a real control (`onOpenList`, which switches tab on a phone). Written by `api/trip/replan` ONLY on the handoff turn and ONLY when `appliedCount > 0` — "trip is planned" over an itinerary nothing was written to is the dishonest-transcript failure this repo has shipped once already — and written BEFORE Penny's reply so it takes the lower `seq`; the live client splices the same bubble into the same place off `planReady` on the applied payload, idempotently, because the heal path re-applies that payload. Penny's own message is now only the honest calls she made: `<handoff_turn>` in `claude.ts` forbids her confirming the save, reciting the route, listing tasks, or closing with an offer. `planReady.test.ts` guards all of it.
    onboardingForm.ts # The onboarding form's shared vocabulary (mirrored to mobile/shared): `QuestionKind`, `TAP_TO_ANSWER_KINDS` (which kinds render chips AND accept a tap — one list, because the two drifted and the date chips went dead), `locksComposer`, every question label, `parseDailyDriveHours`, `cityFromPlace`/`intentPlaceholder`.
    onboardingProgress.ts # The step counter as ONE pure function (`computeOnboardingProgress`), reading which steps are in the flow from the trip's own form_question rows + the scan stash. It was derived in three places and each lied differently.
    tripCompletion.ts # Pure "is this trip over?" — a trip is completed when its LAST leg date is strictly before the user's today (derived, never stored: `trips.trip_status` is exactly that mistake). Today is always passed IN, resolved once via todayISOInZone/todayISO, so there is one notion of today. Mirrored to mobile. `lastDayFromLegDates` (detail views, which have leg dates) / `lastDayFromSchedule` (the trips list, which doesn't — same one-day-per-leg + progress-anchor rule getTripFull uses, surfaced as the derived `Trip.last_day_iso` on the listTripsForUser payload only). Both trip lists show a quiet "Completed" badge; both itineraries then put EVERY day behind the existing "behind you" disclosure ("Show past days") and render nothing ahead. Unit-tested.
    vehicleProfile.ts # Vehicle range/fuel calculations
    fuelCache.ts      # Lazy fuel-cache TTL (FUEL_CACHE_TTL_MS = 48h) + isFuelCacheFresh; shared by server/fuel.ts and LegCard day-open loader
    fuelPlanErrorSemantics.ts  # Fuel plan error handling
    google/directions.ts       # Server-side Google Directions API
    finn/             # The fuel-stop engine (deterministic core). See docs/design/finn-fuel-agent.md
      index.ts        # Barrel re-export (range, route, stationFilter, plan, tank-state)
      range.ts        # Single-range (R) reachability math
      route.ts        # Project a station onto the route polyline (alongKm + detour proxy)
      stationFilter.ts # Eligibility filter: drop truck-only / private stations (classifyStation)
      plan.ts         # Greedy multi-stop placement (planLegFuelStops) — price-preference aware
      sourcingOrder.ts # Pure "which earlier days must be sourced before day N" (legsNeedingSourcingBefore) — the lazy-sourcing dependency cascade
    fuelPricing/      # Region-pluggable price layer (tri-state PriceResult). See finn-fuel-agent.md
      coverage.ts     # Static country capability map (feed vs no-price countries)
      coordinator.ts  # Runs providers (bulk feeds → per-station Google) → PriceResult per station
      providers/      # tankerkoenig.ts (DE feed, bulk) + google.ts (fuelOptions, per-station fallback)
    penny/
      context.ts      # Builds context for Penny from trip data
      geo.ts          # Geo utilities for Penny
      schedule.ts     # Deterministic rest-day/leg-order materializer + route-continuity fixes (computeStartFixes — every leg must start where the previous ended); pure. Applied by trips.repairLegContinuity
      fuelTankState.ts # Pure continuous-drive tank math (km burned since last refuel); only actual fuel stops/trip start refill — rest days & overnights are NOT implicit refuels. DB shim: server/fuel.ts
      planSummary.ts  # Deterministic DB-derived plan facts (day counts, dates, totals, ETA via dayModel, deadline check) — source of truth for plan numbers shown to the user; Penny's prose must NOT state them
      sanitize.ts     # Strips/ detects tool-call markup leaked into Penny's text (she must emit prose only, never <invoke>/<parameter> XML)
      autoContinue.ts # Pure helper for server-side auto-continue: appends a continuation nudge to the message list without breaking user/assistant alternation when a planning turn truncates (used by claude.ts loop)
      contiguityGate.ts # Pure pre-dispatch delete_leg gate (extracted from the replan route 2026-07-02): simulates the turn's actions and blocks only deletes that create a NEW >50km gap relative to the trip's CURRENT gap baseline. The old inline version compared against "zero gaps", so one pre-existing gap anywhere made EVERY delete permanently blocked — the "delete all stops after Tromsø" incident: 36/36 deletes rejected while Penny's already-streamed prose claimed success. Suffix/prefix (tail/head) deletes can never create a gap and now always pass. Unit-tested.
      legPlacement.ts # Pure add_leg placement inference (2026-07-02): when Penny passes no after_leg_id/sort_order, addLeg (repos/trips.ts) inserts the new leg right after the LAST existing leg whose END is within 50km of the new leg's START, instead of blindly appending at max+1. Fixes the batch-insert bug where legs 2..N of a multi-add stretch (only the first carried after_leg_id) landed after the trip's final leg and continuity repair then manufactured a 3,383km "driving day". Explicit placement always wins; no coord match still appends (so sequential trip building is unchanged). Unit-tested.

A mismatch = the pipeline overrode an edit Penny's already-streamed prose describes. The replan route logs it (`penny:edit-overridden`, success=false → /admin/errors) and ships `overriddenEdits` in the applied payload; deriveApplyOutcome folds it into partialApplyWarning (no ChatPanel change — live + heal paths both get it). Metrics (distance/time) deliberately unchecked — re-routing recomputes them legitimately. Unit-tested (editOverride.test.ts).

LLM only transcribes; server re-validates each field. EXACT start date auto-skips trip_date with a confirm note; inferred range is stashed in trips.onboarding_scan and PREFILLED on the vehicle step (confirm-don't-assume — safety number). All-null result ⇒ ask normally. Extensible: add a nullable field + validated mapping

Onboarding turns null into ONE clarifying "what time of year?" question, then a "start today" fallback — start_date_parsed is NEVER null

      otp-email.ts    # OTP email sending
```
