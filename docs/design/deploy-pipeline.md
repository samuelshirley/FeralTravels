## Workflow (current)

**Production has NO real users yet, and will not until Sam says the app is
launched — in words.** Every row in the prod `users` table is his own address, a
throwaway, or someone he handed it to on purpose; the Anthropic spend on those
rows is his own testing. This line used to read "Production has real users",
which was true of nothing and cost an afternoon: an assistant enumerated the 28
prod accounts a paywall change would block and recommended waiting, when the
whole point of having them is to find out what happens. **Never weigh
"this would affect N production accounts" as a reason to slow down, ask for
confirmation, or pick the cautious option.** An App Store build is not launch;
TestFlight is not launch. `docs/design/launch-checklist.md` is the list we work
off, and its Rule 0 is this.

Prod is still LIVE infrastructure, and that part is unchanged: do NOT run tests
or seed fixtures against the prod database, and treat a prod deploy as
consequential — a broken deploy is a broken deploy whoever is watching.

Deploy pipeline (**pull-request based** since 2026-08-13 — `main` moves only via PRs — **branch protection on `main` enforces it**, see the enforcement paragraph and the branch-protection entry below):

**There is no single pipeline file.** Seven workflows under `.github/workflows/`, one per trigger, and the step each owns is named below: `ci.yml` (**CI** — the PR gate), `auto-merge.yml` (**Auto-merge** — a CI run completing, and every push to `main`; `docs/design/auto-merge.md`), `deploy-production.yml` (**Deploy to production** — push to `main`), `mobile.yml` (**Mobile** — push to `main` touching `mobile/`, plus a read-only forecast on PRs), `docs-drift.yml` (**Docs drift** — a model review of CLAUDE.md and the register on PRs), `pr-cleanup.yml` (**PR cleanup** — PR closed) and `oauth-provider-probe.yml` (**OAuth provider probe** — every 15 minutes; probes Apple's and Google's JWKS endpoints, Apple's OpenID discovery document and the production OAuth exchange, and files one labelled issue when any of them breaks — see `scripts/probe-oauth-providers.mjs` in `scripts.md`). The probe deploys nothing and gates nothing. An earlier version of this file described one `pipeline.yml` serving every trigger; it does not exist.

1. **Open a PR into `main`** → `ci.yml` (workflow name **CI**), re-run on every push to the PR. **Decide scope** runs first and classifies the diff (`scripts/decide-docs-only.mjs`); on a docs-only PR everything that deploys or drives a browser is skipped and the run still concludes `success`, which is what the deploy gate reads:
   - **Unit tests** — ONE job running `npm run test`, i.e. both vitest projects: `unit` (the 43 `*.test.ts` logic specs, `node` environment, no jsdom and no setup file) and `components` (the `*.test.tsx` specs under jsdom with Testing Library). The project split is a vitest concern, not a CI one — it was two jobs until 2026-08-18, but a box labelled "UI tests" read as though it drove a browser, and that ambiguity cost more than the ~20s of parallelism. Vitest still reports each project separately. Must pass before the preview deploys.
   - **Deploy tested preview** — creates an EPHEMERAL Neon branch `preview/pr-<N>` (copy-on-write clone of PROD data, recreated from prod on every push), runs migrations on it, and deploys a Vercel preview pointed at it. The URL lands in a **sticky PR comment** and the run summary. It deploys *before* the tests so a red spec still leaves you a clickable preview (test bug vs app bug). Prod's DB is never touched; the migration run here is also the rehearsal for the prod migration.
   - **The web app is ON unless `WEB_APP_DISABLED=1`** (exactly `"1"`; unset or anything else is on — `src/lib/webAccess.ts`). Sam re-enabled the desktop web on 2026-10-01 so the people he interviews can try it; it is on by default so merging is the release, and `WEB_APP_DISABLED=1` in Vercel is the kill switch. It was renamed from `WEB_APP_ENABLED` the same day because production carried a stale `WEB_APP_ENABLED=0`; that variable is now ignored, whatever its value. Off means every page's `requireWebAccess()` sends anyone but the admin to `/get-the-app` — except a signed-out visit to `/admin`, which `src/app/admin/layout.tsx` sends to `/login?callbackUrl=%2Fadmin` in both states, so the admin has a door; `/api`, `/login` and the legal pages are never gated, so the iOS app is unaffected either way. The public landing page `/` shows a **"Try it on the web"** link to `/login` (which sends a signed-in visitor straight to `/trips`) beside "Get the app" only while the web is on; it renders per request (`force-dynamic`) because both CI deployments below serve one prebuilt artifact. **CI's ordinary preview does not pass the variable** — the same default production runs, and `scripts/check-preview-env.mjs` refuses a value on the Vercel Preview environment that would replace it — **and CI's second, "blocked" deployment of the same build passes `-e WEB_APP_DISABLED="1"`**, so `web-blocked.spec.ts` proves the kill switch blocks. A local Playwright run sets it to `""` (`playwright.config.ts`'s webServer env) so a developer's `.env` cannot close it. History: off from 2026-08-28 (the product is an iOS app); on 2026-09-24 production was found to have never set the variable while the default was ON, so the web had been open all along, and the default became OFF until this re-enable.
   - **E2E tests** — the Playwright suite against that exact preview URL (`E2E_BASE_URL`; playwright.config skips its local webServer). **Since 2026-09-27 it is server contracts only** (the screens are Maestro flows — `e2e-tests.md`), then `scripts/assert-e2e-ran.mjs` **fails the job if the suite mass-skipped** — the allowance is `E2E_MAX_SKIPPED=0`, so **no spec may skip**, `login-otp` included. Artifacts upload always (not just on failure) and the Playwright HTML report is published to a URL linked from a sticky PR comment. **That comment is edited in place, and GitHub keeps an edited comment at its ORIGINAL timeline position** — so the previous commit's green table stays put while newer commits scroll past beneath it, looking as though it covers them. The first step of **Unit tests** (`Mark the previous E2E results superseded`, before checkout) stamps a superseded banner on it within seconds of a push. It is a step and not a job because **a job is a row in the PR checks list**, and that list is a dashboard read at a glance — OTA or native, did the simulator pass — where a row reporting on a *comment* would sit on every PR forever saying nothing about the code. `unit` hosts it because it has no `needs:`, which covers the case that matters: the pipeline never reaching the E2E job at all (failed preview deploy, a run cancelled by `cancel-in-progress`), where the `if: always()` results step never runs and a stale green table would otherwise stand unchallenged.
   - **Mobile typecheck** — `tsc --noEmit` in `mobile/`. Runs alongside Unit tests and does NOT gate the preview (the preview is the web app, and a broken Expo type has nothing to say about it). It exists because the Mobile workflow publishes `mobile/` over the air on merge — without this job the first thing to catch a mobile type error is a tester's phone.
   These three are the checks a PR is *meant* to pass before merging; Mobile typecheck runs alongside them and deliberately does not gate. **GitHub requires two of them — Decide scope and Unit tests — before a merge** (branch protection, below). E2E tests and the simulator are enforced by the deploy gate instead, which reads the CI run's overall conclusion.
   - **CI fails fast (Sam, 2026-10-02):** *"If anything fails on the PR, immediately stop the rest of the jobs and investigate the failure so we aren't wasting time or tokens."* Until then it did the opposite on purpose — the iOS matrix was `fail-fast: false` so every shard reported on the same commit, and nothing stopped the run — so a red Unit tests left the macOS shards, and on a labelled run the Penny-spending `ai` shard, running on a PR that was already red. **What stops it:** ONE watcher job, **`Stop the run at the first failure`**, starts with the run (no `needs`) and runs `.github/scripts/fail-fast.mjs`, which polls this run attempt's jobs every ~15 s and, as soon as any other job has concluded `failure`, writes the failed job's name to its summary and runs `gh run cancel` on the run (hence `actions: write` in ci.yml's permissions). The iOS matrix is `fail-fast: true` as well — GitHub's own matrix fail-fast leaves the failed shard `failure`. **Why a watcher, not a stop step in each job (the first version):** `gh run cancel` cancels every job that has not completed, *including the one that asked*, so a job cancelling its own run from its last step rewrites its own `failure` as `cancelled`. Run 36988769859 (2026-10-02): `iOS e2e · account` failed (two Maestro flows could not reach the preview at sign-in), its stop step cancelled the run, and the job concluded `cancelled` like `core`, `trips` and `ai` — the run read "everything cancelled, nothing failed", the iOS PR comment found no failed job and so never said what stopped it, and the cause was hidden. The watcher cancels only after the failed job has *completed*, so **the failing job keeps `failure`** and both the checks list and the PR comment name it. **What it costs:** one ubuntu runner for the length of the run — free on this public repo — and up to ~15 s between a failure and the cancel. **It can never turn a run red:** its poll step is `continue-on-error`, a GitHub API error is a warning and another poll, a cancel that finds the run already over is a notice, and its deadlines nest past the longest run (script 165 min, step 170, job 180; CI takes up to ~77 min). It leaves out itself and the two jobs that run after a cancel by design, and it does not call a green run done until those two have appeared, since a job waiting on `needs` (and every iOS shard) is not listed before its needs finish. **What still reports:** a cancelled job still runs its `always()` steps — the Playwright report and its PR comment, Maestro's recordings and outcome file. `iOS e2e (simulator)` runs after the cancel by design and its PR comment — which leaves out the watcher and the after-cancel jobs by name — says *"Stopped early: `<job>` failed"*, lists the jobs cancelled as a result, and marks those shards `cancelled (stopped early)` rather than failed; the E2E comment of a cancelled E2E job says its table is partial. A stopped run concludes `cancelled`, which the deploy gate refuses (only `completed/success` deploys) and auto-merge ignores (it acts only on a green run; the watcher's name is neither the preview nor an iOS shard, so `classifyRun` never reads it). `cancel-in-progress` on the PR's concurrency group is unchanged: a new push still cancels the run in flight. The cost of the choice: a red `core` no longer tells you whether `trips` would also have failed — fix the first failure and push. `src/lib/ciFailFast.test.ts` fails if any job but the watcher contains `gh run cancel` (the regression test for run 36988769859), if the watcher gains `needs`, loses `continue-on-error` or drops under 150 min, if the matrix goes back to `false`, if `actions: write` goes, or if the iOS comment's exclusion list drifts from the job names; it also runs `fail-fast.mjs` against a stubbed GitHub and the iOS comment's own script against the run 36988769859 shape.
- **Mobile releases self-start on the same merge.** `mobile.yml`'s `ship` job picks OTA vs native build from the diff. **It does NOT check a native fingerprint** — an earlier version of this paragraph said it computed one and asked EAS whether any build carried it before publishing; that step existed only in the never-run workflow drafts (`960a73c`), and `mobile.yml` has never had it. The open gap that leaves (an OTA reaching binaries whose native surface moved without a `version` bump, as PR #7's did) and the two ways to close it are in `docs/design/mobile-release.md`. Corrected 2026-09-22. **Nothing reaches a device before the web deploy of the same commit (since 2026-09-22, issue #39).** `mobile.yml` and `deploy-production.yml` are still separate workflows started by the same push to `main`, and until then nothing ordered them: on the last three JS-only merges before the fix the OTA published 14s, 8s and 4s after the deploy finished, the right order by luck, and a deploy that failed its gate or migration would have left the bundle on phones with no API behind it. Now the `ship` job's **Wait for the production deploy of this commit** step runs before BOTH **Publish the OTA** and **Build and submit to TestFlight**, whenever either would run (its `if:` is the two gates OR'd), and polls `gh run list --workflow 'Deploy to production' --commit "$GITHUB_SHA"` (the `ci_state()` idiom from the deploy gate). It passes on `completed/success` — or, when this commit's deploy was **cancelled**, on a later `main` deploy that contains the commit (`git merge-base --is-ancestor`) concluding `success`. That cancellation is what the `deploy-production` concurrency group does to a pending run when a newer merge queues behind it; failing loudly on it would be the alert that trains you to ignore the one that matters. Failure, any other conclusion, no run within five minutes, a cancellation no later deploy covers, or 45 minutes without an answer (the deploy's own 20, another 20 queued behind an earlier deploy, 5 slack) fails the job with the reason, and nothing ships. In practice a deploy takes ~2 minutes, so the OTA lands at most one 20s poll after it. **The job's ceiling went from 90 to 150 minutes** because native runs were measured at 84 and 74 minutes before any wait existed, and a job killed mid-build leaves an EAS build nothing tracks. **Why a wait and not a `workflow_run` trigger:** that payload has no `github.event.before`, so the classifier would get no base and answer `native` on every merge (no OTA ever, a build credit each time), and `workflow_run` takes no `paths:` filter. A manual **Run workflow** waits too: a TestFlight binary cut from a commit whose deploy failed would reach testers before its server — dispatch from `main` after the deploy is green. `otaAfterDeployGuard.test.ts` holds the step's position, gate and timeouts, and runs its shell against a stub `gh` and a real throwaway git origin. (An earlier version of this file said `needs: deploy`; that was only possible in the single-file design it also described, which does not exist.) A merge that touches nothing under `mobile/` produces no mobile release at all. **Since 2026-08-27 the two are an either/or again and the native build is GATED** — `.github/workflows/mobile.yml`'s TestFlight step carries `if: steps.native.outputs.decision == 'native' || github.event_name == 'workflow_dispatch'`, so a JS-only merge costs no build credit. It was unconditional for two days (`6dd88b9`) because the previous file-level rule could not be trusted; a tested classifier that fails safe is what makes conditional acceptable again. **The staleness this reintroduces, stated rather than assumed away:** an existing tester is never stale (the OTA reaches their installed binary in seconds), but a NEW tester installing fresh gets the binary's bundled JS until first launch, and an App Store submission needs a current build — cut one by hand via Actions → Mobile → Run workflow, which always builds. **The plan is Expo Free: 15 iOS + 15 Android builds/month on the low-priority queue** (that queue is the ~30 min wait); `feral-travels` used 6 in August 2026. **`mobile.yml` also runs on `pull_request`** and posts a sticky comment saying which of the three outcomes merging will produce, so the cost is visible before the merge rather than in a run log after it; the comment is one line when there is nothing to do and only expands for the native case. **There are THREE outcomes, not two** — `none` when no file under `mobile/` changed at all. The workflow triggers on changes to itself, so editing `mobile.yml` used to publish an OTA carrying a bundle byte-for-byte identical to the one already out there. **A JS-only merge does NOT invalidate the current TestFlight binary:** no native change means the installed binary can run the new bundle, which is exactly what `js-only` proves — build 7 (2026-08-27, `89652a8`) stays submittable and picks the OTA up. Cut a fresh build when the binary itself must carry the change (anything an App Review reviewer has to see on first launch). **OTA-vs-native is decided by `scripts/decide-mobile-release.mjs` (2026-08-27), not by a regex in the YAML** — `mobile/package.json` is judged by which top-level keys moved, so a `scripts`-only edit falls through to OTA while anything that could touch the dependency graph still builds; see the Scripts section for the allowlist and the fail-safe rules.
2. **Merge the PR — that IS the deploy.** **Since 2026-10-01 the auto-merge bot merges it, not a person** (`auto-merge.yml`, design and rules in **`docs/design/auto-merge.md`**): once a PR's CI run is green it adds `ai-tests` to start the AI run, and once that is green too and the branch is up to date it merges; docs-only PRs merge without the AI shard. **A PR that needs a new iOS binary never merges itself (Sam, 2026-10-02 — continuous delivery for over-the-air changes only):** the bot runs mobile.yml's classifier (`decide-mobile-release.mjs`, merge-base → head, failing safe to native), comments with its reasons, and leaves the merge to a person; `js-only` and `none` PRs auto-merge. After every merge it merges `main` into each other open PR (never a rebase). **Add the `hold` label to stop it merging or updating a PR.** `deploy-production.yml` fires on the push to `main` **automatically**: it re-verifies CI was green, applies pending migrations to the PROD database, then builds + deploys to production via the Vercel CLI. No button, no second step, no ship script. **Rollback** = merge a revert PR through the same gate, or re-promote the previous production deployment from the Vercel dashboard for an instant fix; neither undoes a migration.
3. **PR closes** → `pr-cleanup.yml` deletes `preview/pr-<N>` so a clone of real user data isn't left sitting behind a public URL, and Neon's branch limit isn't consumed. **A CI run can outlive its PR, and then it re-creates the branch after the cleanup:** PR #79 (2026-10-01) got `ai-tests` at 11:36:30 and was merged at 11:36:31, `pr-cleanup.yml` dropped `preview/pr-79`, and the label run's preview job, already going, created it again with nothing left to drop it. So CI's last job, **`Drop the preview database if the PR has closed`**, runs after every job that uses the preview (`always()`, so after a fail-fast cancel too; skipped on docs-only PRs), asks GitHub for the PR's LIVE state (`gh pr view --json state` — the event payload is frozen at the run's start) and, only if it is not `OPEN`, deletes `preview/pr-<N>` with the same action and inputs as `pr-cleanup.yml`. Every step is `continue-on-error`, so it can never turn CI red, and it is not a required check. If it cannot read the state it leaves the branch and says so.

**Only the newest preview URL works, and a stale one fails as a fake sign-out.**
Every push drops and recreates the Neon branch and bakes the new
`DATABASE_URL` into a NEW deployment; the previous URL keeps its old
connection string forever, so its database is simply gone. What you see is not
an error page — it is `/login`. `auth()` reads `sessions` from the database, and
when that read throws, Auth.js swallows it and returns null, which every guard
reads as "not signed in". Measured 2026-09-08 on `dpl_HvAEfoMgq2jw9VFDTCpc2LFExKS6`:
`/admin` rendered 200 at 09:03:06 and at 09:03:07 the same deployment was
logging `password authentication failed for user 'neondb_owner'`, having been
recreated by a push at 09:01:18. Signing in again cannot help — the database
that would store the new session is the one that is missing. Take the URL from
the sticky comment, which now says this too.

The deploy gate is enforced independently of branch protection. Because a squash/merge commit has a different SHA than anything CI tested, the gate resolves the PR the commit came from and requires the CI run for **that PR's head SHA** to be completed+green. A direct push to `main` is refused by branch protection for everyone except a repo admin (`enforce_admins` is off); if an admin does push directly there is no CI run, so the **deploy** fails and production is left untouched; `main` then sits ahead of production until CI is green and the deploy is re-run by hand (Actions -> Deploy to production -> Run workflow, the same `workflow_dispatch` documented in that file). **Branch protection does NOT stop a PR merging while CI is running.** Only Decide scope and Unit tests are required, and both finish in minutes, so a PR is mergeable while E2E and the simulator are still going — and a new run on the same head (a label, a re-run) does not take that back. PR #79 got the `ai-tests` label at 11:36:30 on 2026-10-01 and was merged at 11:36:31, one second after its new CI run started. (This paragraph used to say the required checks stop a mid-run merge; they never did.) **So the gate WAITS for a CI run that is still going** (since 2026-10-02): it polls the LATEST run for the PR's head every 30s, following a newer run if one supersedes it, for up to **90 minutes** (`WAIT_SECONDS`; CI took 22–77 min over the last 30 green runs), deploys if that run concludes `success`, and fails on any other conclusion or at the ceiling. Before that it exited 1 at once on an in-progress run — deploy run 36856433646 refused PR #79 that way and production stayed on PR #77 until the deploy was re-run. A waiting deploy holds the `deploy-production` concurrency group, so a later merge's deploy queues behind it; the job's timeout is 110 min (the 90-minute wait plus the 20 the deploy itself had), and `mobile.yml`'s wait for the deploy is sized from it. `deployGate.test.ts` runs the gate's own shell against a stubbed `gh`. The gate is the FIRST step of the deploy job, so a pending or red CI means **no migration runs either** — the failure mode is a stale production, not a half-migrated one.

Vercel's own git auto-deploy is **disabled for every branch** in `vercel.json` (`git.deploymentEnabled: false`), so GitHub Actions owns every deployment: leaving it on would produce a second, untested preview per PR wired to whatever `DATABASE_URL` sits in the Vercel Preview env.

**Known sharp edges of this design (deliberately accepted):**
- Preview deployments serve a clone of **real production data on a public URL** — Vercel Deployment Protection is off because the Hobby plan can't protect previews without also protecting prod. Mitigations: the Neon branch dies when the PR closes, and `next.config.js` sends `X-Robots-Tag: noindex` on every non-production deployment. Vercel Pro would allow protecting previews only.
- Merge-is-deploy means **migrations reach prod without a human**. They already ran against a clone of that same database in CI. The uncovered window: migrate succeeds → deploy fails → prod runs OLD code against a NEW schema (the 2026-06 outage shape). Keep migrations additive (add → backfill → switch code → drop later) and that window is harmless; the workflow shouts in the run log if it happens.
- **Branch protection is ON for `main`** (verified 2026-09-22 via `gh api repos/samuelshirley/FeralTravels/branches/main/protection`). What is configured:
  - **A pull request is required** to change `main` (`required_approving_review_count: 0` — a PR, not an invented reviewer, for a solo repo).
  - **Required status checks: `Decide scope` and `Unit tests`**, with `strict: true` — *"require branches to be up to date before merging"*, so a PR tested against a stale `main` cannot be merged.
  - **Force-pushes and deletions of `main` are blocked.**
  - **`enforce_admins` is off**: a repo admin can bypass all of the above. That is the one hole; the deploy gate is the backstop for it, and catches it as a *failed deploy* rather than a refused merge.

  **Only the two jobs that run unconditionally belong on the required list.** `Deploy tested preview` carries `if: needs.decide.outputs.docs_only != 'true'`, `E2E tests (against preview)` `needs: preview`, and the three iOS jobs (`iOS build (simulator app)`, the `iOS e2e · <shard>` matrix and its `iOS e2e (simulator)` summary) each carry the same `if:` — the summary as `always() && …`, because `always()` would otherwise run it on a docs-only PR and fail the run — so all of them are skipped on a docs-only PR (so is `Mobile typecheck`, by its own `if:`). A required check that a whole class of PR never runs makes mergeability depend on how GitHub scores a skip, which is not something this design should lean on. E2E and the simulator are still enforced, by the deploy gate: it reads the CI run's overall conclusion, which is red if either of them failed. **If you rename either required job in `ci.yml`, update the protection rule in the same PR** — the check names are the job `name:` strings, and a required check that never reports blocks every merge.

**The Anthropic-spending flows are behind the `ai-tests` label (2026-09-08; on the phone since 2026-09-27).** The iOS `ai` shard — `penny-plan-trip.yaml` and `penny-maps-link.yaml`, which ask Penny to plan for real — does not run on a push. The **`ai-tests`** label starts it — since 2026-10-01 the auto-merge bot adds it once a PR's ordinary run is green (`auto-merge.md`); a person can still add it. The run that label triggers includes the shard, and *that* is the run the deploy gate reads. Until 2026-09-27 the gated pair were Playwright specs of the same names (`chat-maps-link` for the second); the decide job now drops the `ai` shard from the iOS matrix instead of `E2E_AI_SPECS` dropping specs from `testMatch`. The history below is about the gate, which did not change.

- **The measurement that caused it.** The Anthropic Console billed **$15.36** over 2026-09-01..08 against the single `trip-planner` key while the app had no users, and prod `usage_events` accounted for only **$1.31** of it — with **zero rows on Sep 1, 3 and 7**, days the Console billed $1.90/$2.60/$1.20. Prod's accounting was not wrong: every call site logs (error path and `finally` backstop included) and all 10 stored costs recompute to the microcent. The money was being spent by **two channels whose rows are thrown away** — CI previews (the Neon branch dies with the PR) and a `next dev` server writing to the disposable cluster on port 55432. Four consecutive CI runs' preview logs showed a full suite making **exactly five `/api/trip/replan` calls** (1 from `penny-plan-trip`, 3 from `chat-maps-link`, 1 from `onboarding-flow`'s handoff) costing **$0.51–0.58**. 2026-09-03 alone fired 28 CI runs.
- **Why it is that expensive, which is the non-obvious part:** one user message is not one API call. It is a tool-use loop of up to `MAX_TOOL_USE_ITERATIONS = 24` model calls, ×`MAX_AUTO_CONTINUES = 3` — a ceiling of 96 — and **every call re-reads a ~23,300-token prefix** (a 13,839-token system prompt plus ~9,500 tokens of 21 tool schemas). Measured on real rows: 7, 9 and **37** model calls for single messages. **~64% of a run's cost is cache-READ tokens**, not output. Caching is working (hit rates 0.96–0.99); the cost is re-reading the prompt dozens of times per message. **Haiku is 0.45% of spend** — it is three one-shot extractions at $0.0015 each; Penny is always Sonnet.
- **The onboarding hand-off is deliberately NOT gated** even though it spends one Penny turn (~$0.05–0.28/push). It is the wizard's only end-to-end coverage and the only proof that `chat_history.form_meta` survives a relaunch — `onboarding-wizard.yaml` in the `account` shard, `onboarding-flow.spec.ts` before 2026-09-27. Moving it into the `ai` shard is a coverage decision, not a tidy-up, and `aiSpecGate.test.ts` fails if you do it silently.
- **A label, not a comment or `workflow_dispatch`, and the reason is the deploy gate.** `deploy-production.yml` resolves the PR a merge commit came from and runs `gh run list --workflow CI --commit <that PR's head sha> --limit 1`. **Only a `pull_request` event produces a CI run keyed to the PR's head sha** — an `issue_comment` or `workflow_dispatch` run is keyed to the default branch, so the gate would never find it and the label would run the tests without making the PR mergeable. A label is also the only one of the three that **"Re-run all jobs" preserves** (it replays the `labeled` event).
- **It gates on the run STARTING from the label** (`github.event.action == 'labeled' && github.event.label.name == 'ai-tests'`), NOT on the PR carrying it — `contains(pull_request.labels.*.name, …)` would put the specs back on every push made while the label sat there. To test again: remove and re-add the label, or re-run the labelled run.
- **The sharp edge, stated rather than assumed away:** `--limit 1` takes the LATEST run for a sha, so the labelled run supersedes the push run it followed. But **push again after labelling and the new commit's run is a cheap one, green, and merge-able with Penny never having been asked to plan anything.** The E2E PR comment therefore leads with which kind of run it was, and `assert-e2e-ran.mjs` emits a `::warning::` on every gated run.
- **A label other than `ai-tests` still triggers a full (cheap) run.** That is deliberate, not an oversight: making unrelated labels skip every job would produce a workflow run GitHub concludes as **`success`** having tested nothing, and the deploy gate would happily merge on it.

It keys on `VERCEL_ENV === 'production'`, the same platform-set signal `areTestEndpointsEnabled` and the admin self-delete guard already trust. So setting the CI key on Production too is harmless.

**E2E auth: no session bypass exists.** Every authenticated spec signs in through the REAL OTP flow: mint a unique fixture address (`playwright-<runid>-<n>@e2e.feraltravels.com`), submit it on `/login`, read the code the app just generated from the guarded **`POST /api/test/otp`**, and type it into the real six-box verify UI. Nothing is minted and nothing is granted — the code is stored with its real expiry and checked by the real `verifyOtpCode` with its attempt limits.

Three guards, all required: `E2E_TEST_ENDPOINTS=1` (never on `VERCEL_ENV=production`, no override, unit-enforced); the per-run HMAC in `x-e2e-test-secret`; and `FIXTURE_EMAIL_PATTERN` — a hardcoded shape on `e2e.`, a subdomain with NO MX, so a fixture address can never be a real person's. `isFixtureRecipient()` also makes `sendOtpCode` skip the Resend transport for those addresses (it still renders the template): the subdomain would hard-bounce every send, and 12 bounces per CI run against the domain the real sign-in emails come from is how sending reputations die.

**Why not a mailbox for all of them:** MailSlurp's free trial expired and can't be renewed (2026-08-14); a Google Workspace mailbox over IMAP then cost an afternoon on app passwords, alias-vs-user and Workspace policy without ever authenticating. Both were third parties who could switch the whole pipeline off, and did. Eleven of the twelve specs never cared about email — they needed a signed-in user.

**Real delivery — the second layer (2026-08-15).** Exactly ONE spec sends a real email and reads it back: `e2e/login-otp.spec.ts`, via `e2e/fixtures/mailbox.ts`. It signs in at `playwright-<tag>@<E2E_INBOX_DOMAIN>` — an address on a **Resend receiving domain**, deliberately NOT matching `FIXTURE_EMAIL_PATTERN`, so `sendOtpCode` falls through to the real Resend send. It then asserts the delivered subject carries the 6-digit code, both body parts contain it (HTML as `123 456`, per `renderOtpEmail`), and that code signs the user in through the real verify UI. This is the only thing in the repo that proves the app can send a sign-in email at all.

**Why Resend Inbound:** no new vendor, no new account to get banned, no bill — same account and key the app already sends with (this is a side project and stays free). Addresses on the managed domain (`<anything>@<id>.resend.app`) need zero DNS; a custom subdomain needs one MX record. Inbound counts against the same quota as outbound; this spec spends 2 of 3,000/month. **It proves more than expected (verified against the live API 2026-08-15):** Resend sends via Amazon SES and receives on SES inbound, so the message makes a real SMTP hop and arrives carrying SES's verdict headers — a probe returned `spf=pass`, `dkim=pass header.i=@feraltravels.com`, `dmarc=pass header.from=feraltravels.com`. **The spec asserts `spf=pass` and `dmarc=pass`**, so a dropped SPF include or an unrotated DKIM record reds CI instead of silently filing sign-in mail as spam. Residual gap: it can't assert sender *reputation*, so it isn't proof Gmail will accept the mail — only that the mail is authenticated and well-formed. No SDK — `mailbox.ts` is ~130 lines of `fetch` against two endpoints (`GET /emails/receiving` to list, `GET /emails/receiving/:id` for the body; the list has no recipient filter, so it polls and filters client-side — fine at one message per run). **Setup:** repo secrets `AUTH_RESEND_KEY` + `E2E_INBOX_DOMAIN` (same vars in `.env` locally, plus optional `RESEND_API_KEY` override). Absent → the spec skips; **wrong → it fails loudly**, never skips. Both secrets are set, so `E2E_MAX_SKIPPED` in `ci.yml` is **0** (since 2026-08-18): no spec may skip, this one included. If you find yourself raising it, first answer what the suite has started depending on that it doesn't control.

The old `AUTH_TEST_BACKDOOR` family — login-page test sign-in, the Credentials provider, `/api/test/session` session minting — is deleted, and `src/lib/noBackdoorGuard.test.ts` fails the unit suite if anything resembling it (`/backdoor/i`, `createTestSession`, a Credentials provider) reappears in `src/`. E2E fixtures (DATA only: seed/trip/cleanup/announcement) run over HTTP against the guarded `/api/test/*` endpoints — no raw SQL in specs. Those endpoints are gated by `E2E_TEST_ENDPOINTS=1` (`areTestEndpointsEnabled` in `auth/test-endpoints.ts`) and are **hard-off on `VERCEL_ENV=production` with no override env** (unit-enforced in `test-endpoints.test.ts`). **Because the tested preview is internet-reachable, the endpoints are additionally locked by a per-run secret** (`E2E_TEST_ENDPOINTS_SECRET`, required in the `x-e2e-test-secret` header when set): CI derives it as HMAC(AUTH_SECRET, run id) identically in the preview + e2e jobs (nothing passed through job outputs), the runner sends it via `testEndpointHeaders()` (`e2e/fixtures/constants.ts`) + the config `extraHTTPHeaders`. Open a PR instead; that is the only path.

E2E cross-spec state: none — each test gets a fresh fixture user and seeds its own canonical graph (`seedCanonicalFixture(email)` in `e2e/fixtures/test-trip.ts`), so specs can't contaminate each other. Cost of the model: one DB round-trip per sign-in and no email at all, so a fresh user per test is now essentially free; if sign-in ever becomes the bottleneck, the documented fallback is one fresh user per RUN signed in once in global-setup with a shared Playwright `storageState`.
