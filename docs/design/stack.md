## Stack

- **Framework:** Next.js 14 (App Router, React 18)
- **DB:** Neon Postgres via `postgres` driver + Drizzle ORM
- **Auth:** NextAuth v5 (beta) — OTP email + Google OAuth
- **AI:** Anthropic SDK — chat agent with tool-use in `src/lib/penny/`. Model IDs are hardcoded in one registry (`src/lib/models.ts`) — no per-request fallback chains; update there when a model is sunset. **The API KEY is resolved in one place too — `src/lib/anthropicKey.ts`** (see the "One Anthropic key was one number" note below); the four call sites (`claude.ts`, `onboardingIntentScan`, `parseStartDate`, `parseRangeEstimate`) all go through `anthropicApiKey()` and none read `process.env.ANTHROPIC_API_KEY` directly. **Penny runs on Haiku 4.5 since 2026-09-09** (`PENNY_MODEL`, was `claude-sonnet-4-6`), and `src/lib/models.test.ts` fails if she goes back — every token type bills at exactly one third of Sonnet's price, so the direction that hurts is a one-word edit in an unrelated commit that nothing warns about and the bill reports a month later. Going back is allowed; it has to be a diff that says so. Measured on the same prompt, same account flow: the Austin 14-leg trip cost **$0.585 over 37 model calls on Sonnet** against **$0.085 over 6 on Haiku**, because Haiku obeys `<batching_for_multi_waypoint_trips>` (all `resolve_place` in one call, all `get_route` in one, all `add_leg` in one) where Sonnet went one at a time. The rulebook in `claude.ts` was written against Sonnet's mistakes, so treat the swap as an experiment with a measurement attached rather than a settled fact. **That measurement is `toolTrace`** — `ReplanResult.toolTrace: string[][]`, one entry per model call listing the tools it emitted, shipped in the applied payload as `toolTrace` + `modelCalls` and persisted in `penny_turns.result_meta`. Its LENGTH is the number of times the ~23,300-token cached prefix was re-read, which is where ~64% of a turn's cost goes; before it, a 37-call turn was a number in a bill with nothing recording what the calls were.
- **Reverse geocoding:** Nominatim (OpenStreetMap) for coords→place-name only — Google's Geocoding API is not enabled on the one key. See `lib/osm/nominatim.ts`; identifying `User-Agent` mandatory, 1 req/s.
- **Email:** Resend
- **Maps:** Google Maps (client JS API + server Directions API for routes + Places `fuelOptions` as a per-station price fallback in `lib/fuelPricing/providers/google.ts` + **Places API (New) `places:searchText`** for name→coords resolution in `lib/google/geocode.ts`). NOTE (2026-07-01): `geocode.ts` uses **Places API (New) only** — the legacy `place/textsearch/json` endpoint and the `geocode/json` Geocoding-API fallback were removed. The legacy endpoint required the deprecated "Places API" SKU (not enabled on the one key) and caused a 100% `REQUEST_DENIED` outage; there is now a single `searchText` call and no cross-product fallback (a miss returns `not_found`/`unavailable`, and the caller asks for a Maps link). **Fuel stations ARE from Google, and the calls are PAID** — `a0c9ee6` (2026-07-22) removed OSM Overpass, OSRM and the whole fuel-pricing layer, so Finn's station search is **Places (New) Text Search along-route** (`lib/google/places.ts`, `searchFuelAlongRoute`, one call per leg planned) and its route geometry is Google Directions (used only when a leg has no stored geometry). `src/lib/osm/` and `src/lib/fuelPricing/` no longer exist. **This note claimed the opposite until 2026-09-09** and cost a whole task's worth of wrong reasoning about cost — if you are about to write "Finn is free", check `src/server/fuel.ts`'s imports first. Every one of those calls now writes a `usage_events` row (`google-places` / `google-directions`); `logGooglePlacesUsage` had NO caller between 2026-06-29 and 2026-09-09, so day-open cost was invisible for ten weeks. `server/fuel.ts` still treats a needed-stop-but-zero-candidates gap as retryable `failed`, never the 48h-cached `no_stations_found` warning (reserved for "stations exist but none reachable"). The Place Photos / Street View "stop photos" feature was **removed 2026-06-30** (see teardown note below). **A place's ROUTABLE identity now travels with it (2026-09-11): `place_id` in, the snapped coordinate out.** Google's coordinate for a large park is the centroid of its POLYGON, which can sit in roadless backcountry — measured on the live key 2026-09-10, `destination=37.2982022,-113.0263005` (Zion NP) returns **ZERO_RESULTS** while `destination=place_id:ChIJ2fhEiNDqyoAR9VY2qhU6Lnw` returns a 1335.1 km / 774 min route. Big Bend's centroid happens to land near a park road, which is why half of one trip planned and half did not, and why this went unseen for months. So `resolve_place` emits `place_id`, `get_route` accepts `origin_place_id`/`destination_place_id` (and one per waypoint), `getDirections` sends `place_id:<id>` in place of the coordinate — **and the LRU cache key includes it**, because the same coordinate with and without an id are different requests with different answers. The second half is free and is the half that lasts: Directions already returns `routes[0].legs[].start_location`/`end_location`, so the snapped points come back as `routable_start`/`routable_end` for `add_leg` to persist (Guadalupe → Zion by id yields `{37.2336032, -112.8751275}`, which then routes on its own in both directions). **A leg row carries no `place_id`**, so plumbing the id only as far as `get_route` would fix the first plan and leave every later re-route — continuity repair, the replan route, Finn's geometry — failing exactly as before, days later, with no user message to explain it.
- **Payments:** Apple IAP through **RevenueCat** (`react-native-purchases` in `mobile/`, no config plugin — it autolinks). The app's only jobs are `Purchases.logIn(users.id)`, rendering the store's Offerings and calling `purchasePackage`; `POST /api/webhooks/revenuecat` is the ONLY thing that may grant access. Setup: `docs/design/iap-setup.md`.
- **Tests:** Vitest (unit), Playwright (web e2e), **Maestro (iOS e2e on a real simulator, `mobile/maestro/`)**
- **Language:** TypeScript throughout, Zod for validation
