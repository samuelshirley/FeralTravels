### Schema (33 tables in `src/server/db/schema.ts`)

users, accounts, sessions, verificationTokens, emailOtpCodes, oauthTokenUses, vehicles, trips, legs, costs, pois, links, gpxTrails, routes, routeLinks, stops, tasks, chatHistory, appMeta, usageEvents, userViewportTime, announcements, announcementDismissals, pennyTurns, deletedUsers, subscriptions, subscriptionEvents, usageAlerts, promoCodes, otpSendThrottle, breakerAlerts, ipRequestCounters, oauthProviderKeys

**`oauth_provider_keys` (migration 0041, 2026-09-21):** one row per OAuth provider (`google`, `apple`) holding the last JWKS that provider served (`jwks`, verbatim) and when it was fetched live (`fetched_at`). It is the fallback the native exchange (`src/server/auth/jwksSource.ts`) verifies against when a live key fetch fails, and it exists because Apple's `/auth/keys` answered 404 to about one request in five on 2026-09-21 while every cold start began with an empty in-memory cache. **Trust:** public keys only, nothing secret — but whoever can write the row chooses what sign-ins are checked against, so it is written in exactly one place (`repos/oauthJwks.ts`, after a successful live fetch, and only forwards in time: an older set never overwrites a newer one) and honoured only while younger than `MAX_STALE_MS` (72h — the reasoning is on the constant). Not user data: account deletion has nothing to do here.

**`subscriptions.pre_revoke_status` (migration 0040, 2026-09-10):** one nullable text column — the status a row held at the moment an admin revoked it, plus the sentinel `'none'` meaning there was no row at all. Column add only; table count unchanged. It exists because `revokeSubscription` overwrites `status` IN PLACE, so without it the previous state is destroyed by the write and the undo has nothing to restore. Written by the revoke (through a `CASE` in the `ON CONFLICT DO UPDATE`, so a double-revoke never records `'revoked'` over the real answer), consumed and cleared by `reactivateSubscription`. See the "A revoke is undoable" note under Subscriptions for the whole design.

**Account deletion — BUILT (migration 0024, 2026-08-20):** users can permanently delete their own account from Settings on **both** web and native. Apple guideline 5.1.1(v) requires an app that creates accounts to delete them *from inside the app*, so the native screen is the requirement and the web page is the mirror — not the other way round. **Immediate and unrecoverable by design: no grace period, no soft-delete, no undo.**

- **Flow:** `DeleteAccountSection` (`src/components/` + `mobile/components/`) → type-to-confirm dialog → `POST /api/me/delete` → `deleteUserAccount` (`repos/accountDeletion.ts`). One route serves both clients because `requireUser` resolves a session cookie **and** an `Authorization: Bearer` token against the same `sessions` table — there is deliberately no native-only deletion path.
- **The confirm phrase is server-enforced.** `src/lib/accountDeletion.ts` (mirrored to `mobile/shared/lib/`, so it is in `SHARED_FILES` in `scripts/sync-shared.mjs`) owns `DELETE_CONFIRM_PHRASE = 'delete account'` and `isDeleteConfirmationValid` (trim + case-insensitive). The route re-checks it, so a UI bug, a stray fetch or a replayed request can't erase an account on its own.
- **Postgres does the deleting.** Every user-owned table cascades from `users.id`, directly or through `trips`, so `DELETE FROM users` is what actually erases the account — a new child table inherits this for free as long as it carries `onDelete: 'cascade'`. **Three things need explicit help and are the reason this isn't a one-liner:**
  1. **Rows keyed by EMAIL, not user id** — `email_otp_codes`, `oauth_token_uses`, `verificationTokens`. A cascade cannot see them and they hold the raw address. Compared with `lower()` on both sides: every writer stores the address lowercased but `users.email` itself is **not** guaranteed to be (the NextAuth adapter inserts the provider's `profile.email` verbatim), so a case-sensitive compare would silently leave behind exactly the rows this code exists to remove. Covered by an e2e test that plants an unconsumed OTP and asserts it is gone.
  2. **Free text inside `usage_events`.** The column is `set null` on purpose so AI spend and the admin error log survive anonymised — but *anonymised is not automatic*: `penny:user-idea` stores the user's own sentence in `error_message`, and `penny:contiguity-gap` stores place names lifted out of their itinerary. Nulling `user_id` would leave those readable in `/admin/errors` forever, so the text is cleared explicitly and only the numbers survive.
  3. **FK indexes.** Postgres does not index a foreign key automatically, and a referential action fires **once per deleted parent row** — so deletion was running an unindexed scan of `usage_events` per trip owned, inside the transaction. Migration 0024 adds `usage_trip_idx`, `sessions_user_idx`, `accounts_user_idx`, `penny_turns_user_idx`. Without them a heavy user could time the function out, abort the transaction, and be **permanently unable to delete their account** — failing hardest on exactly the people with the most data.

  All in one transaction, so a mid-way failure leaves the account intact rather than half-erased. Reads are sequential, not `Promise.all`: a drizzle/postgres-js transaction runs on one reserved connection.
- **`deleted_users` is the only trace left.** Stores `email_hash` (**HMAC**-SHA256 of the normalized address, keyed with `DELETED_USER_ENC_KEY` — one-way, answers "did this address ever have an account?"; it is an HMAC and not a bare SHA-256 because email addresses are enumerable and CI puts a clone of prod behind a **public** preview URL, so a plain digest column could be attacked offline from a dump), `email_encrypted` (AES-256-GCM under the same key, readable only via `/admin/deleted`), account created/deleted timestamps, sign-in providers, and trip/vehicle/chat counts. `sign_in_providers` reads `accounts` first, but that table is written **only** by the NextAuth adapter (web OAuth) — the native exchange mints a user with no `accounts` row, so an empty result falls back to `oauth_token_uses` (`native-oauth`) before assuming `otp`; without that every iOS Google/Apple user would be mislabelled. NOT unique on the hash — sign up, delete, sign up, delete again is two deletion events worth counting. **The key is optional on purpose:** missing or malformed → `encryptEmail` returns null, the row stores the hash alone, and the deletion still completes. A user's right to leave must never depend on our churn bookkeeping succeeding. Crypto lives in `src/server/deletedUserCrypto.ts`; every decrypt failure mode (no key, wrong key, tampered, wrong version) returns null rather than throwing.
- **Admin self-delete is blocked on PRODUCTION ONLY** (`VERCEL_ENV === 'production'` + `isOnAdminAllowlist`). The allowlist is hardcoded to one address, so deleting it in prod would take the admin dashboard, the error log and the ops-alert recipient with it, irreversibly. Previews leave the guard off so the full flow can be exercised against the PR's throwaway database.
- **The confirm dialog's emphasis (2026-09-07):** the phrase to type is set in the SEMIBOLD face on both platforms (the face the armed Delete label uses — at `medium`/body weight it read as part of the sentence and people typed "delete"), and the DISARMED Delete button carries no danger colour at all (transparent fill, neutral border, subtle label) so a mismatch in the box does not look like a button ignoring the tap. Web: `DeleteAccountSection.test.tsx`; native (no test runner): `src/lib/deleteAccountEmphasisGuard.test.ts` reads the component as text.
- **Surfaces:** `/admin/deleted` (decrypted addresses, tenure, churn counts, plus a warning banner when no key is configured) and a "Deleted accounts" stat card on `/admin`. `cleanupPlaywright` drops the fixture address's tombstones so local e2e runs don't fill that page with `playwright-*` noise.
- **Env:** `DELETED_USER_ENC_KEY` — 32 bytes, base64 or hex (`openssl rand -base64 32`). It keys BOTH columns, so **rotating it makes every row written under the old key permanently unreadable and stops `wasEmailDeleted` matching them.** Set it once in Vercel (production *and* preview) and leave it. Unset is a supported degraded mode (hash-only, bare SHA-256, `/admin/deleted` shows a banner) so a local checkout with no secrets still deletes correctly.
- **Trap worth knowing:** root `middleware.ts` redirects cookie-less requests outside `PUBLIC_PREFIXES` to `/login`, and `/api/me/delete` is not listed — but the app lives in `src/app`, so Next.js does **not** pick up a root-level `middleware.ts` and the bearer-authenticated native call reaches the route (which 401s itself). If middleware is ever moved to `src/middleware.ts`, the native delete button starts 307ing into an HTML login page — an App Store 5.1.1(v) rejection. Every other `/api/*` route the app calls has the same exposure.
- Tests: `src/lib/accountDeletion.test.ts`, `src/server/deletedUserCrypto.test.ts`, `e2e/account-deletion.spec.ts`. The privacy page (`(legal)/privacy`) documents the retained tombstone — keep it in sync if the columns change.

**Answered onboarding steps keep their options (migration 0034, 2026-09-08):** one nullable `chat_history.form_meta` jsonb, written on `form_answer` rows only. `chat_history` stored just `content`, so the moment a setup step advanced, the options the driver had chosen FROM were gone — they only ever existed on the live onboarding API response — and scrolling back through setup showed a flat transcript of a form nobody could see the shape of. The row now carries the question it answers, the options as offered, and which one was taken (`ChatFormMeta` in `types/trip.ts`).

- **On the ANSWER row, not the question row**, because that is the first moment both halves are known: one insert, no update-later path, no window in which a half-written step could render.
- **`collapseOnboardingSteps` + `answeredChips` + `buildFormMeta` (`src/lib/onboardingForm.ts`, shared) are the one definition.** The two clients cannot share a renderer — a `<span>` with inline styles against a `<View>` with a StyleSheet — so what travels is the DECISION: which rows fold together, and which chip is lit. The server calls `buildFormMeta` when it persists the row and each client calls it again for the optimistic render, so a step cannot change shape on reload. `onboardingForm.test.ts` fails if either ChatPanel starts working it out for itself.
- **Two deliberate non-collapses.** A step that offered NO options (the free-text opening description) keeps its plain question-then-answer bubbles — there is no widget to redraw and one enormous pill is worse than what it replaced. And the composite `vehicle` card is ONE client answer over TWO server steps, so `clientRecordsAnsweredStep` keeps the client out of it and the vehicle answer keeps its plain bubble.
- **`redrawsAsAnsweredStep(meta)` is that first rule, and it is a PREDICATE because three callers must agree (fixed 2026-09-08).** They didn't: `collapseOnboardingSteps` skipped zero-option steps, while both ChatPanels drew the widget for any `form_answer` carrying `form_meta` — and the server writes meta on **every** one of them (`buildFormMeta` at `onboarding.ts`, unconditional). So the opening description got the worst of both: its question bubble stayed AND its answer became the pill, meaning the driver's own opening words were no longer a user bubble anywhere. It is a **type guard**, not a boolean, so the renderers cannot narrow `meta` by hand and drift again. Caught by `onboarding-flow.spec.ts` on PR #28 — the first CI run those assertions ever had, since the branch's previous run predated the commit. Guards: `ChatPanel.answeredStep.test.tsx` reproduces the whole thing in jsdom in ~1s (a five-minute preview deploy is a bad feedback loop for a render rule), plus a source guard in `onboardingForm.test.ts` that both ChatPanels gate on the predicate. **That source guard also repaired a silent one:** the "answered chips are inert" test slices the renderer block with `indexOf`, and when the anchor string drifts `indexOf` returns `-1` while `slice(-1, n)` still yields a non-empty string — so its web half had stopped guarding anything. It now asserts the anchor was found.
- Pairing is by label against the NEAREST EARLIER unclaimed `form_question` row, which matters because the clarify path and a `range_help` detour both re-ask a label; the row that stands in for the step has to be the question the driver was actually looking at. Rows written before this migration carry no meta and render exactly as they always did.
- **This is the THIRD position on answered steps, and the design doc records two.** §7d of `docs/design/nocturne-reskin.md` asked for `Check` + a one-line receipt; item 9 of `docs/bugs/mobile-web-nav-units-prompt.md` cancelled that in favour of ordinary chat bubbles. Neither is what ships now.
- Tests: `src/lib/onboardingForm.test.ts`, and `e2e/onboarding-flow.spec.ts` asserts the lit chip both live and **after a reload** — the reload half is the only thing that proves the column, since the optimistic render would pass without it.

**Penny turn resilience — `pennyTurns` (migration 0018, 2026-06-30):** one durable row per Penny replan turn, independent of the SSE stream the client reads. Fixes the "Something went wrong. Please try again." false-failure bug: that bubble is a **client-only** `catch` in `ChatPanel.tsx` (the PWA backgrounded mid-turn tears down the fetch and `reader.read()` throws); the server keeps running and persists Penny's reply regardless (Vercel request cancellation is opt-in via a `vercel.json` `supportsCancellation` flag — `vercel.json` exists but only disables git auto-deploy and never sets that flag, so cancellation is off and turns are not lost). `pennyTurns` lets a dropped client **re-attach/reconcile** (heal the false error) instead of dead-ending, gives the server an **idempotency** anchor (`idempotency_key` unique — a retry/double-send can't spawn two concurrent replans), and persists a **`queued`** turn so a send fired while another is in flight survives the app closing and runs after (drained by the finishing invocation). Status: `queued | running | done | error`. Diagnostics for client-only stream failures go to `usage_events` (`provider = 'penny:client-stream-error'`) via `POST /api/analytics/client-error`. See `docs/design/penny-turn-resilience.md`. **Build status (FULLY WIRED 2026-06-30):** schema + repo + #1 diagnostics + the full #2–#4 wiring are done. `POST /api/trip/replan` now creates a turn (idempotent on `idempotency_key`), runs it via the extracted `runTurnWork`, marks it `done`/`error` on the row, and after the foreground turn finishes **drains any `queued` turns inside the same still-alive request** (`drainQueuedTurns`, atomic `claimNextQueuedTurn`, capped at `MAX_DRAIN_TURNS=5`) — chosen over `unstable_after`, which isn't available in Next 14.2.35. A turn that queues behind an in-flight one returns JSON (`{ turn }`) instead of an SSE stream; an idempotent replay returns the existing row. New `GET /api/trips/[id]/turns?key=` (reconcile/poll endpoint, read-only). Client (`ChatPanel.tsx`): each send carries an `idempotencyKey` (stored as `turnKey` on the assistant bubble), handles the JSON-vs-stream branch, and **heals the false error bubble** by reconciling the durable record on stream-throw, on stream-incomplete, and on `visibilitychange`/`focus` (re-attach on reopen). Apply logic is the pure `deriveApplyOutcome` (`src/lib/penny/applyOutcome.ts`, unit-tested), shared by the live-stream and heal paths. **Concurrency model (migration 0019, 2026-06-30):** every send is inserted as a `queued` turn (`createTurn`, deduped on `idempotency_key`) and then tries to claim the trip's single execution slot via `promoteTurnToRunning`. A **partial unique index** `penny_turns_one_running_per_trip_idx` (`UNIQUE (trip_id) WHERE status = 'running'`, migration 0019) makes the claim **atomic and DB-enforced**: a second concurrent send's promotion raises a unique violation, caught in the repo (`isUniqueViolation`/`23505`) → returns null → the turn stays `queued` and is drained by the running request. `claimNextQueuedTurn` (drain) routes through the same promotion, so two concurrent drains can never put two turns `running`. This closes the check-then-insert TOCTOU — **two distinct concurrent sends can no longer both start a replan on one trip** (queued backlog of N is still allowed; the index only constrains `running`). **Apply migration 0019 with `db:migrate`.**

**What a turn RECORDS (2026-09-11).** `result_meta.turnTrace` holds, per model call, each tool's
name, its input, the result content handed back and whether it went back as `is_error` — written
from the same `tool_result` blocks the model was shown, so the record cannot disagree with what
actually ran. Before this it stored tool NAMES only, and investigating the 2026-09-10 Zion turn
meant re-running `resolve_place` by hand and guessing that the coordinates matched the ones Penny
had been handed. No migration — `result_meta` is already jsonb. Rules, all in
`src/lib/penny/turnTrace.ts`: fields are capped at **2,000 chars** and the whole trace at **64,000
chars**, and a cut is always marked (`truncated`, `omitted_model_calls`) because a trace that
silently loses its tail reads as a complete record of a shorter turn; overflow drops the NEWEST
model calls, since a failure cascade is read from its start; and the system prompt is a **16-hex
fingerprint of the assembled prompt plus the tool-schema set**, never a copy — it is ~13,800 tokens
and byte-identical across every call in a turn, so storing it per turn would be megabytes a month
for no information (recovering the TEXT of an old prompt would need a prompt store keyed by hash
and is deliberately not built). **Size:** a 9-call / 28-tool-call turn of the Zion shape lands
around 10–15 KB, hard-capped at 64 KB. It is **stored, never streamed** — the `applied` SSE payload
does not carry it and `GET /api/trips/[id]/turns` strips it back off, because the browser has no
use for several KB of tool inputs on a heal. **Deletion is already covered and was verified against
a real database, not assumed:** both `penny_turns.user_id` and `.trip_id` are `ON DELETE CASCADE`,
so account deletion removes these rows outright — unlike `usage_events.error_message`, which
survives deletion by design and therefore needed an explicit scrub. `npx tsx scripts/dump-trip.ts
<trip> --trace` prints it. Retention stays the known gap below, and traces make the rows bigger.

**Residual notes / known gaps (reviewed):** (1) **Idempotency-key dedup is fully enforced** (unique index on `idempotency_key`) — a retry/double-send of the SAME turn (the "Please try again" button, the common cause) cannot spawn a second replan. (2) **One-running-per-trip is now DB-enforced** (see Concurrency model above) — the prior TOCTOU is closed. (3) Queued turns drain **in-request** (not a background job): if the foreground invocation is *killed* between `markTurnDone` and `drainQueuedTurns`, a turn queued behind it can sit `queued` until the client's poll deadline (~5min, then a "reopen in a moment" notice) — a *subsequent* send self-heals it (it promotes itself and its drain picks up the backlog). A background sweeper would fully close this; deferred. (4) Retention/pruning of `penny_turns` rows is unaddressed (transient diagnostics-grade).

`trips` carries a driver-progress anchor (`current_leg_id`, `current_lat/lng`, `progress_anchor_date`, `progress_updated_at`) set by the `reportPosition` tool; `getTripFull` re-anchors every leg's `date_iso` from it, and the itinerary collapses legs before `current_leg_id` as "behind you". An explicit report is a **floor**, not a freeze — `behindCutoffRank` (`src/lib/dates.ts`) takes the max of the report and the calendar, so a stale report no longer pins the view (the days-old "frozen itinerary" bug).

**User timezone — "today" is the driver's wall clock, not the server's (migration 0017, 2026-06-30):** new nullable `users.timezone` (IANA string, e.g. `"Europe/Oslo"`) is captured from the browser on load via `Intl.DateTimeFormat().resolvedOptions().timeZone` (no geolocation permission — distinct from GPS) and PATCHed to `/api/me/preferences` by `UnitsContext` (once per page-load). It's the single source of truth for the user's current day. Server "today" now resolves through `todayISOInZone(tz)` (`src/lib/dates.ts`, UTC-fallback when null/invalid) everywhere it used to call `todayISO()` for trip logic: leg-date anchoring in `getTripFull`, Penny's `context.today`, and the `report_position` anchor (`applyTripProgress`). **Bug it fixes:** the server runs in UTC on Vercel while the client collapses days in browser-local time, so a UTC-stamped anchor vs a local cutoff drifted a day near midnight and showed the day-you're-on as "behind you / completed". The client cutoff still uses browser-local `todayISO()` (already the user's zone). Repo helpers: `getUserTimezone`/`setUserTimezone` (`repos/users.ts`, re-validates the zone against Intl before persisting). The "behind you" header now reads "N earlier days" (not "completed" — the cutoff is positional, not proof the days were driven). **Related fix (same change):** the geolocation prompt was consolidated to one on-load request. (Superseded 2026-07-12: the whole client GPS flow now lives in `DeviceLocationContext` — see the "Client GPS pipeline unified" note below — which keeps the single-prompt policy and adds permission-change reactivity.)

**Device location → Penny (migration 0020, 2026-07-01):** the browser Geolocation position captured on app open is now fed to Penny so "my current location" / "where I am" / "plan from here" work without the user typing coords. Flow: `TripWorkspace` gets `getCurrentPosition`, best-effort reverse-geocodes it client-side (`lib/reverseGeocode.ts`, Maps JS Geocoder — the already-enabled key), and POSTs `{lat,lng,place_name}` to `/api/trips/[id]/position`. `updateTripPosition` stores them in `trips.last_known_lat/lng` (existing) + the new **`last_known_place`** text column (migration 0020; only overwritten when a label resolves, so a geocode miss never wipes a good name). `buildPennyContext` projects these as `context.device_location = {lat,lng,place,as_of}` (null when GPS never granted). The Penny prompt (`claude.ts` `<reporting_progress>` + the context-field doc) tells her to use `device_location` directly as the coords for `report_position` and NOT ask the user to type a location when it's present. This is DISTINCT from `trip.current_place` (the progress anchor Penny sets via `report_position`) — the bug was that Penny only ever saw her own anchor, never the device GPS, so she "never knew where the user was" despite the browser having permission. **Apply migration 0020 with `db:migrate` BEFORE deploying** (code selects the new column). Table count unchanged (24) — column add only.

**Past-day fuel suppression (2026-07-01):** legs in the collapsed "Behind you" section no longer lazily source fuel on open or show the "Planning fuel stops…" spinner. `Itinerary` passes `isPast` (cutoff membership — NOT `date_iso < today`, so the *current* leg still plans fuel even if a stale progress anchor left its date in the past) → `LegCard` (skips the lazy fuel effect) → `StopsSection` (suppresses the planning spinner). Opening an old day is instant and quiet.

**Declared tank state (migration 0021, 2026-07-12):** three nullable `trips` columns — `declared_range_km`, `declared_range_leg_id` (plain uuid, no FK — same stale-pointer contract as `current_leg_id`), `declared_range_at` — written by the **declareFuelState** Penny tool (see Penny Tools). Table count unchanged (24) — column add only.

**Daily driving hours (migration 0033, 2026-09-04):** one nullable `trips.daily_drive_hours` integer — the onboarding `trip_pace` answer (or the scan's transcription of "5 h days"). Null falls through to `DEFAULT_MAX_DRIVE_HOURS_PER_DAY` (8); Penny's context carries it as `trip.daily_drive_hours` and `executeGetRoute` splits long segments on `min(it, 8)`. The leg validators keep 8h as the hard ceiling regardless. Editable through `PATCH /api/trips/[id]` (`daily_drive_hours`, 1–8 or null); there is no Penny tool for it yet, so mid-trip "make my days shorter" is answered by pointing at the trip's setup. **The number is now SAID (2026-09-11).** It decides how many days a trip takes — `get_route` splits on it — and it appeared nowhere: not in Penny's prose (she must not author it), not on the plan summary, not in Settings, so a driver reading "six days" had no way to learn that six was arithmetic on a number they never saw. `dailyPaceLine` (`src/lib/planReady.ts`, mirrored) puts it in the deterministic `plan_ready` message, and says out loud when the number is OURS rather than theirs — presenting the 8 h default as the driver's own choice is the small lie that makes the rest of the numbers untrustworthy. Both clients now render the plan-ready BODY from the stored row rather than from a constant of their own, so a row written at one pace cannot be drawn at another; rows written before this keep rendering exactly the two paragraphs they hold. **Still not editable after setup** — a per-trip editor is the follow-up, and Settings is the wrong home for a per-trip number. **Apply migration 0033 with `db:migrate` BEFORE deploying** (code selects the new column). Column add only.

**Client GPS pipeline unified (2026-07-12):** `components/DeviceLocationContext.tsx` is now the ONE client geolocation owner: the on-load prompt, a live `watchPosition`, and a Permissions-API `onchange` subscription. `TripWorkspace`'s position report and `useNextStop` (smart nav) consume the shared context; neither calls the Geolocation API directly. **Bug it fixes:** `useNextStop` checked the permission once at card-expand — if the state was `'prompt'` (popup on screen, unanswered) it locked to `'unavailable'` for the whole mount, so granting did nothing and desktop showed the location popup AND the full 3-button nav list simultaneously (trip d0b5741b). Smart-nav selection is extracted to pure `pickNextStop`/`segmentDestinations` (`lib/useNextStop.ts`, unit-tested). Related same-incident fixes: `public/sw.js` no longer caches Next.js **RSC payloads** (`_rsc`/`RSC: 1`/`text/x-component` are excluded like `/api/` — the stale-trips-list-in-PWA bug; CACHE_NAME v6), and `add_stop` rejects stops within **1 km of the leg's end coords** (the duplicate-destination-button incident; see `<app_ui_awareness>` in `claude.ts` — Penny now knows what the nav UI shows and must never answer a display complaint with a data write).

`trips.onboarding_scan` (jsonb, migration 0012) is a transient stash mirroring `pending_intent`: the first-message intent scan (`onboardingIntentScan.ts`) writes validated, prefill-confirm onboarding values here (currently the fuel-range safety numbers) until the question that owns each comes up on the vehicle step; cleared at handoff. The start date isn't stashed — an exact one is applied immediately and its question skipped. See `OnboardingScan` in `types/trip.ts`.

**Single fuel range (migration 0025, 2026-08-25):** the vehicle has exactly ONE range metric — **`vehicles.range_km`**. The old comfortable/hard-max pair ("max stretch") is gone: migration 0025 renamed `comfortable_range_km` → `range_km` and dropped `hard_max_range_km` (the two-number model was too confusing — range is just range). Finn treats `range_km` as the never-exceed ceiling; the C→H "stretch zone" in `lib/finn/` is deleted, and a station void longer than the range now yields a forced-stop reason + the honest gap warning instead of a silent stretch. The `effective_range_km`/`computeEffectiveRangeKm` alias is also collapsed — `normalizeRangeKm` (`vehicleProfile.ts`) is the one guard. Captured in onboarding as the single range question; shown in Settings as the single "Refill every" stat. Bounds remain `FUEL_STOP_SPACING_KM_MIN/MAX` (200–1500). **Lazy fuel sourcing — BUILT (migration 0013, 2026-06-26):** fuel stops are now sourced **lazily on day-open**, not eagerly across the whole trip during planning (the old eager fan-out was the Google Places cost sink). New column `legs.fuel_stops_updated_at` is the cache timestamp; `FUEL_CACHE_TTL_MS` (48h, `src/lib/fuelCache.ts`) is the staleness window shared by server + client. Flow: the initial plan creates legs/routes only (no fuel calls — Penny's prompt no longer auto-calls `plan_fuel_stops`; she keeps it for **explicit** "find fuel for day N" asks). When the user expands a day, `LegCard`'s effect POSTs `/api/legs/[id]/fuel-stops`, which routes through `planFuelStopsForLegLazy` (`server/fuel.ts`): a terminal-success leg (`ready`/`no_stations_found`) sourced within the TTL is a **cache hit with zero Places calls**; never-sourced or stale legs run the real `planFuelStopsForLeg` search (algorithm untouched) and (re)stamp the cache. `setFuelStatus` stamps the timestamp on terminal-success and clears it on `none`. **Invalidation is affected-leg-only, never a trip-wide re-fan-out:** `invalidateLegFuelCache` (a leg's coords change via `update_leg`, `report_position` re-routing the upcoming leg, or continuity-repair) and `invalidateTripFuelCache` (vehicle/range change on `PATCH /api/trips/[id]`) reset `fuel_status='none'` + drop auto option stops so the affected day re-sources on next open. The "stale → **cheap** price re-check" the design calls for is Finn's separate pricing task (not built — no US price feed); until then a stale cache falls through to a full re-search, kept infrequent by the TTL gate. The trip-wide fan-out (`replenishFuelStopsForTrip` + `POST /api/trips/[id]/fuel-stops/replan` + `api.replenishFuelStops`) was **fully removed 2026-07-02** — lazy per-leg day-open sourcing is the ONLY fuel path; don't reintroduce a whole-trip fan-out. **A dependency CASCADE is not that fan-out, and is required (2026-09-09).** The tank walk in `fuelTankState.ts` reads earlier days to find the last refuel, and a day that was never opened has no fuel stop — which is indistinguishable from a day that genuinely needed none. So opening a late day first accumulated every unopened day's full distance as burn: on trip `ab824cde` day 11 that was **2,396 km against a 500 km range**, and the driver was told "Next fuel is 44 km ahead — beyond safe range (-1896 km)" about a real station on a full tank, cached as `no_stations_found` for 48 hours. `planFuelStopsForLeg` now sources every unsourced DRIVE leg between the last real refuel and the target, oldest first, before planning it. **Bounded by the refuel, not by the trip.** **The cost is real and was mis-stated here when this note was first written (2026-09-09):** the objection that killed the old fan-out was *paid Google Places calls*, and Finn still makes them — one Places Text Search per leg planned — so opening day 12 cold on a 12-day trip costs up to ~6 searches instead of 1. It is still the right trade (a wrong fuel warning is worse than a few cents) but it is a trade, not a freebie, which is why every Places and Directions call now writes a `usage_events` row. The decision of which legs is pure and unit-tested in `lib/finn/sourcingOrder.ts`; a leg another request holds (`computing`/`pending`) is reported and the target bails with a retryable `failed` rather than two writers racing on one leg's stops. A leg already `ready`/`no_stations_found` is left alone even with no stop — it HAS been searched, and "none needed" is an answer the walk is entitled to believe.

**The planner cannot describe arithmetic as geography (2026-09-09).** `planLegFuelStops` returns a discriminated union — `planned` / `gap` / **`tank_state_invalid`** — instead of a `gap: boolean`. A burn at or past the range (`R − B <= 0`) makes every candidate unreachable, so the old code fell into the gap branch and produced the negative-range sentence above; that string is now unrepresentable rather than merely unlikely. `tank_state_invalid` maps to a retryable `failed` with a `usage_events` row (`finn:fuel-plan`, success=false → /admin/errors), never the 48h-cached `no_stations_found`, which stays reserved for its real meaning: stations exist, none reachable, on a tank state that made sense. After the cascade it should be unreachable; the log is how we find out if it is not. Guards: `plan.test.ts`, `sourcingOrder.test.ts`, `fuelEmptyStateGuard.test.ts` (both platforms' "no stop needed" copy), and the second case in `e2e/lazy-fuel-sourcing.spec.ts`. **`failed` legs DO re-source on day-open (2026-06-30):** `LegCard`'s `needsFetch` now includes `fuel_status==='failed'` (not just `none`/stale-success). The old rule skipped `failed` to avoid re-hitting *paid* Google Places on every expand. That cost is NOT gone (the OSM cutover was reverted by `a0c9ee6`), so this is a deliberate trade: a leg stuck on a stale error is worse than one extra search, and auto-retry self-heals legs stranded on it (`'computing'`/`'pending'` are still skipped — search in flight). **The dedupe is an IN-FLIGHT flag, not a signature (item 6, 2026-09-04):** LegCard used to remember `${id}:${status}:${updated_at}` across renders, and an INVALIDATED leg (`none`, no timestamp) is byte-for-byte the signature its own first auto-source recorded — so after Penny moved a day's destination the refetch was swallowed, the open day read "No stops yet" with no spinner, and collapsing/re-expanding could not change the signature either; only a full reload fixed it. Guard: `LegCard.fuelResource.test.tsx` (mutation-checked) and the second half of `e2e/chat-maps-link.spec.ts`.
