# Task: v1.0 cleanup — delete what shipped, what was cut, and what only ever described those

Read CLAUDE.md first (it is one of the things you are cleaning up, so read it as evidence, not
as gospel). Its "Reproduce, never guess" rule applies: every deletion below is preceded by a
reference check and followed by `npx tsc --noEmit && npm run test`, and nothing is deleted on the
strength of this list alone — the list is where to look, the grep is the proof.

## Why (reasoning, so you can make judgement calls the list doesn't cover)

The owner has declared the app **version 1.0 as it stands today**. Everything that describes a
future the codebase didn't take, a bug that was fixed, a feature that was cut, or a migration
that already ran is now noise — and this repo has a specific pattern of noise: documents written
as a running commentary of incidents that nobody re-reads, but that every tool re-loads.

The costliest single example is `CLAUDE.md`: **193 KB, ~48k tokens**, loaded into every Claude
Code session. It began as "a map so you don't scan the codebase" and became a changelog of
every incident since June, most of them about code that no longer exists (dump stations, travel
style, stop photos, vehicle remediation, MailSlurp, `ship.sh`, the nightly replan). That is the
same accretion pattern as Penny's 13k-token system prompt, which was measured 2026-09-09 to be
half the per-turn API cost. Same disease, same cure: keep the map, move the history to git,
which already has it.

Principles for anything not listed:
- **Git is the archive.** Deleting a doc loses nothing; `git log --all -- path` recovers it.
  Do not create an `archive/` folder — that is the same noise with a different name.
- **A doc earns its place by being needed to OPERATE v1.0** — deploy it, sign it, submit it to
  Apple, debug it in production — or by describing a decision that is still open. A doc that
  explains how something was built is history; the code and its tests explain how it works.
- **A script earns its place by being runnable against v1.0 and useful more than once.** A
  backfill or migration that already ran against production is done; keeping it invites
  someone to run it again.
- **Prefer deleting a test over keeping dead code for it**, but never delete a test that guards
  live behaviour. When a deletion breaks a test, read the test: if it guards the thing being
  deleted, delete both; if it guards something else through it, fix the test.
- **Dormant database columns are dropped, not documented as dormant.** Additive-only rule from
  CLAUDE.md still applies: drop columns in a migration AFTER the code stops reading them, in
  the same PR (the code half deploys before the migration only if the migration fails, which
  is the safe direction for a drop).
